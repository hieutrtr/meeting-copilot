## Privacy audit (R-3.8-3 + R-3.8-5)

Goal: privacy-mode picker UX never names API keys; backend gate fires before any handshake / API-key read.

- `src/privacy/privacyMode.ts` — `tooltipFor` returns strings of the shape `"Deepgram is a cloud STT provider — disabled in {Mode} mode. Switch to Cloud mode to enable."`. PM-S19 asserts `not.toMatch(/_API_KEY/)` for every blocked cell. `_mode` (and the rest of the matrix) is fully decoupled from key names.
- `src/components/CloudConsentBanner.tsx` — fixed wording, no string interpolation, no `console.*`. CB-U3 asserts the rendered text never includes `_API_KEY`, `DEEPGRAM`, or `ELEVENLABS` (case-insensitive).
- `src/components/SettingsSheet.tsx` — picker option labels come from `labelFor(id)` (existing T-3.6 helper, returns `"Deepgram"` / `"ElevenLabs"`); the `disabled — disabled` suffix is constant. The `title` attribute reads from `tooltipFor` (sanitised above).
- `crates/stt-mlx/src/providers/privacy.rs` — `factory_with_privacy` returns `PrivacyModeViolation { mode, kind }` BEFORE calling `factory(...)`. The match is short-circuit; the disallowed branch never reads `cfg.api_key`. The two short-circuit tests prove this directly: they pass `api_key: None` and assert the privacy variant wins (would otherwise be `SttError::Config("DEEPGRAM_API_KEY missing")`).

**Conclusion:** No new key-leak path. The existing T-3.6 / T-3.7 audits remain in force — T-3.8 only ships UI gating + a backend short-circuit that runs *before* any key is read.
