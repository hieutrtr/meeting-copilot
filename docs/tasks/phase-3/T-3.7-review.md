## Privacy audit (R-3.7-3)

Goal: assert API keys NEVER reach any output surface.

- `src/tts/featureFlag.ts` — no `console.*` calls; reads env var only.
- `src/tts/elevenLabsTts.ts` — no `console.*` calls (`grep -rn "console\." src/tts/` returns 0). The constructor stores the key in a private field; `buildRequest` writes it into the `xi-api-key` header (the only correct destination); error throws compose from `res.status` + `res.statusText` only — no key, no body echo.
- `src/components/AnswerPanel.tsx` — the new Speak button label is composed from a fixed `speakStatus` enum (`"Speak answer"` / `"Speaking…"` / `"Speak again"` / `"Speak failed — retry"`); never includes the key, never includes the user text. Error path catches the `onSpeak` rejection without echoing the message into the DOM.
- `crates/stt-mlx/src/tts/elevenlabs.rs` — `ElevenLabsTtsConfigError` constructor message is `"ELEVENLABS_API_KEY missing or empty"` (env-var name only); the `Display` impl on `TtsError::Config` prepends `"config error: "` so the rendered string is `"config error: ELEVENLABS_API_KEY missing or empty"` — env-var name, never key value. The HTTP error-on-non-2xx path (Phase 3.x live wiring) MUST follow the same rule; documented in the file header.
- T-3.9 telemetry log will add an explicit grep gating `apiKeys.elevenlabs` against the log surface. Owed but scheduled, not shipped here.

**Conclusion:** T-3.7 introduces no leak path. The follow-up enforcement (telemetry grep) is correctly scheduled in T-3.9, not T-3.7.
