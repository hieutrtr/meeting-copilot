## Privacy / security review checklist

- [x] **No regression Phase 1 / 2.** All 552 carry-forward vitest cases still pass; Rust crates untouched.
- [x] **API key never logged.** `apiKey, api_key, key, secret, token, password` are all in `FORBIDDEN_KEYS`. The scrubber drops the entire event on any forbidden key, so a buggy upstream that piggybacks `apiKey` on a switch event cannot leak it.
- [x] **Privacy mode constraint enforced at backend, not just UI.** Out of scope for T-3.9 — handled by T-3.8's Rust `factory_with_privacy`. T-3.9's append loop is privacy-mode-agnostic by design (it logs the *transition* events, never enforces them).
- [x] **Telemetry log does NOT contain transcript / audio content.** TM-S13 explicit grep gate over 100 events (case-insensitive substring match against the full `FORBIDDEN_KEYS` list). The allow-list of top-level event fields means a future schema extension that adds a new forbidden field will fail closed (the field wouldn't be in `ALLOWED_KEYS`).
- [x] **Disk-fill bounded.** `maxBytes = 10 MB` × `maxFiles = 3` archives → ~30 MB worst-case (current + 3 archives). Sized for desktop deliverable; reviewed against an 8h meeting projection.
- [x] **Default opt-out.** New users get `telemetryEnabled = false`. UI checkbox is the single point of opt-in.
- [x] **No `git push`.** Local commit only.
- [x] **No backwards-compat shims.** Schema field is additive; `coerceLoaded` zero-fills missing field from defaults (consistent with the existing v2 migration shape — no key bump needed).
- [x] **No comments rot.** Comments document the *why* (privacy invariants, opt-in promise, rotation cadence) and reference the AC line for each invariant.

| **R-1** A future provider adds a new content field (e.g. `words[]`) that bypasses `FORBIDDEN_KEYS` | TM-S5 pins the documented list; allow-list of top-level event fields fails closed (unknown field → drop). | Low — any extension to event schema must thread through the allow-list, which forces a privacy review. |
