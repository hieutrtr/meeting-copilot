## Goal

Layer bounded reconnect onto the Deepgram WebSocket adapter and prove session continuity
across mid-stream connection drops. End-state:

1. A new `BackoffConfig` struct (initial / multiplier / max-delay / max-retries / jitter)
   on `DeepgramConfig` — defaults bounded under the 10 s wall-clock AC, designed so T-3.4
   ElevenLabs reuses the same shape.
2. `DeepgramAdapter::connect_with_backoff` — exponential, jittered backoff loop wrapping
   the existing `connect()`. Surfaces config errors immediately (not retried), wraps
   transient I/O failures into `SttError::ProviderUnavailable { attempts, last_error }`
   when the budget is exhausted.
3. `SttProvider::transcribe_chunk` routes the lazy-connect through `connect_with_backoff`;
   send-side I/O failures drop the socket so the next chunk re-triggers the budget.
4. `SttError::ProviderUnavailable { attempts, last_error }` — additive enum variant
   distinct from `Io(String)`. Caller can pattern-match "transient blip" vs "provider
   down — escalate to user".
5. Chaos test: in-process mock server accepts two sequential connections on one port,
   sends a finalized `Results` envelope on each then closes mid-stream. The adapter must
   reconnect transparently between calls and emit both segments with correct
   meeting-relative timestamps (session base re-anchors per reconnect).

### Scope boundaries

- **TLS / `wss://`**: still deferred. T-3.2 punted TLS to T-3.3 in its review, but the
  T-3.3 AC ("reconnect within 10 s; 3-strike rule emits typed error") is independent of
  the transport layer. Adding rustls features at the same time as reconnect would
  conflate two API surfaces and double the no-cargo verification surface. TLS lands in
  T-3.6 (settings test-connection button) — the "test connection" path is the first
  caller that genuinely needs `wss://`. Reconnect logic is identical for plain `ws://`
  and `wss://` (tungstenite hides the transport behind `MaybeTlsStream`).
- **Cross-call failure counter**: T-3.3 tracks attempts within a single
  `connect_with_backoff` call. A sticky cross-call counter would let the UI surface
  "provider degraded" warnings; deferred to T-3.9 (telemetry) where the event log is the
  natural store for cross-call signals.
- **Helper-daemon wiring**: helper-daemon stays on `default-features = false` (no
  `deepgram` feature). Provider switch (and therefore reconnect surfacing) lands in T-3.6
  + T-3.8.
- **Chunk-level replay buffer**: not implemented. Deepgram streaming is best-effort; the
  in-flight chunk on a dropped connection is lost (Deepgram itself doesn't replay
  buffered audio across sessions). T-3.9 telemetry will count drops so the UX can
  surface "N seconds of audio re-sent on reconnect" if the rate gets noisy.

### Backoff schedule (default)

| Attempt | Pre-attempt sleep (no jitter) | Cumulative wall-clock |
|---|---|---|
| 1 | 0 ms | 0 ms |
| 2 | 200 ms | 200 ms |
| 3 | 400 ms | 600 ms |
| Budget exhausted → `ProviderUnavailable { attempts: 3 }` | — | ~600 ms + jitter |

With `jitter = 0.25` (default), each sleep is uniformly distributed in `[0.75d, 1.25d]`;
worst-case wall-clock = ~750 ms. Floor 1.0 enforced on `multiplier` so the schedule is
monotonic non-decreasing (a `multiplier < 1.0` would shrink delays forever — pathological
config caught by `backoff_next_delay_normalizes_sub_one_multiplier`).

### Mid-stream drop semantics

```
caller (transcribe_chunk loop)        DeepgramAdapter                    server
─────────────────────────────         ──────────────────                  ──────
chunk N                       ──────► connect_with_backoff() (1 attempt)  accept conn 1
                                      send PCM binary frame              ─────►
                                      drain text frames                  send Results (final)
                                      Message::Close received            close
                                      socket = None
                              ◄──────  Vec<Segment> (1 element)
chunk N+1                     ──────► socket.is_none() → connect_with_backoff()
                                      attempt 1 connects                 accept conn 2
                                      session_base_ts_ms = chunk.ts_ms
                                      send PCM binary frame              ─────►
                                      drain text frames                  send Results (final)
                                      Message::Close received            close
                                      socket = None
                              ◄──────  Vec<Segment> (1 element)
```

The chaos test (`mock_ws_reconnects_after_mid_stream_drop`) asserts both segments arrive,
text bytes are unchanged, and the second segment's `start_ts_ms` re-anchors to chunk
N+1's `ts_ms` — proves the meeting timeline survives the reconnect.

## Risk + Mitigation

| Risk | Impact | Mitigation |
|---|---|---|
| Chaos test flake on slow CI (server thread doesn't move to second `accept()` before client reconnects). | Intermittent test failure. | 150 ms grace sleep between adapter calls + 100 ms server-side read timeout per connection. Both far above sub-ms localhost RTT. Total test wall-clock < 1 s on a healthy host; budget set to fail loud (not hang) on a sick one. |
| `SttError::ProviderUnavailable` enum variant breaks an exhaustive caller. | Compile fail in helper-daemon / src-tauri. | Grep verified: 0 exhaustive matches on `SttError` outside the crate. The 3 in-crate matches (`provider::tests`, `providers::mod#tests`, `providers::deepgram#tests`, `providers::mlx#tests`) all use `other => panic!()` catch-alls. Helper-daemon uses `#[from] SttError`. |
| Reconnect storm if a misbehaving server accepts then immediately closes. | High reconnect rate, log spam, cost overrun (Deepgram per-second billing during reconnect handshakes). | Bounded `max_retries = 3` per call; subsequent calls also bounded. T-3.5 cost meter will surface elevated handshake billing; T-3.9 telemetry will count consecutive `ProviderUnavailable` events. Cross-call sticky counter deferred per scope. |
| `clock_jitter_sample` collisions in tight loops (multiple adapters constructing on the same nanosecond). | Identical jitter across parallel reconnects → coordinated reconnect spike. | `subsec_nanos()` resolution is nanoseconds — collision probability negligible at the 200 ms+ inter-attempt cadence. Crypto randomness is overkill. T-3.9 telemetry will surface if this matters in practice. |
| `connect_with_backoff` total wall-clock exceeds 10 s under pathological config. | AC violation (10 s reconnect ceiling). | Default schedule bounded at ~750 ms (with jitter); `max_delay` cap (3 s) ensures even an extreme `max_retries = 10` stays at ~30 s — acceptable margin. T-3.6 settings UI will not expose `max_retries` as a user knob. |
| Send-side socket failure leaks the in-flight chunk's PCM. | One chunk lost on each reconnect. | Documented in code comment as "best-effort"; T-3.9 telemetry counts loss events. Production Deepgram itself batches across chunks (final segment timing slips by ~200 ms anyway), so a lost chunk usually rounds to a slight quality dip rather than a missing word. |

Live Deepgram chaos verify (manual, requires `DEEPGRAM_API_KEY` + TLS — gated until
T-3.6):

1. Start a Deepgram session with `transcribe_chunk` looping on real PCM.
2. Disable Wi-Fi for 2–5 seconds; re-enable.
3. Adapter should resume within ~200 ms after Wi-Fi recovers (first attempt succeeds
   post-reconnect).
4. Disable Wi-Fi for 30+ seconds (longer than the budget).
5. Adapter should surface `SttError::ProviderUnavailable { attempts: 3 }` to the caller
   within ~700 ms of the first failed chunk; UI displays a red banner ("Deepgram
   unavailable — switching to MLX").

## Cost Tracking

T-3.3 adds zero runtime cost: tests use a fake API key against a localhost mock server.
Per ARCH §13: a reconnect storm could elevate Deepgram billing (handshakes are billed),
so the bounded `max_retries = 3` budget is the cost ceiling per call. T-3.5 cost meter
will surface elevated reconnect-driven cost; T-2.7 cost guard catches threshold.

## API-Key Handling

`api_key` handling is **unchanged** from T-3.2: read from `DEEPGRAM_API_KEY` env var,
sent only over the WebSocket upgrade `Authorization` header, never logged. T-3.3 adds
no new code paths that touch the key.

`SttError::ProviderUnavailable.last_error` carries the underlying `tungstenite::Error`
display string. Tungstenite's display formatter does **not** include header values, so
the API key never leaks into this field. T-3.9 telemetry will explicitly grep for
`Token ` substrings as a defense-in-depth assertion.
