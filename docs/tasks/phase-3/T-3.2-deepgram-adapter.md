## Goal

Ship a sync, per-chunk Deepgram STT adapter that plugs into the `SttProvider` trait already
extracted by T-3.1. End-state:

1. A new module `crates/stt-mlx/src/providers/deepgram.rs` holding `DeepgramConfig` +
   `DeepgramAdapter` (the latter implements `SttProvider`).
2. `ProviderKind::Deepgram` + `ProviderConfig::Deepgram(DeepgramConfig)` variants wired into
   `factory(...)` (gated on a new `deepgram` cargo feature, default-on at the crate level —
   helper-daemon stays `default-features = false`).
3. A typed-error path when `DEEPGRAM_API_KEY` is missing/empty: `SttError::Config(String)`
   surfaces at construction time, before any network IO.
4. A mocked-WebSocket structural test driving the full adapter→server round-trip with a
   golden Deepgram `Results` JSON, asserting:
   - The upgrade request carries `Authorization: Token <key>`.
   - PCM is sent as a binary frame (linear16 little-endian).
   - Interim hypotheses are filtered out (Phase 2 question detector reads only `is_final`).
   - Finalized JSON → `SttSegment { text, start_ts_ms, end_ts_ms, is_final = true }` with
     timestamps offset against the first chunk's `ts_ms` (session base).

### Deepgram WebSocket — endpoint shape

Per ARCH §3.2:

```
wss://api.deepgram.com/v1/listen?model=nova-2&encoding=linear16&sample_rate=16000&interim_results=true
Authorization: Token <DEEPGRAM_API_KEY>
```

The adapter sends PCM as binary frames; Deepgram replies with text frames containing JSON
envelopes:

```json
{
  "type": "Results",
  "is_final": true,
  "speech_final": true,
  "start": 1.5,
  "duration": 2.3,
  "channel": {
    "alternatives": [
      {"transcript": "What time is the meeting?", "confidence": 0.987}
    ]
  }
}
```

`type` may also be `Metadata`, `SpeechStarted`, `UtteranceEnd`, etc — non-`Results` envelopes
are silently dropped. For `Results`, the adapter ignores `is_final = false` (interim) and
only emits when `is_final = true` AND `channel.alternatives[0].transcript` is non-empty.

### Trait shape — streaming source through a sync per-chunk API

`SttProvider::transcribe_chunk(&mut self, chunk)` is sync request/response (Phase 1 T-1.5
contract; ARCH §3.1's async-stream is the IPC envelope, not the per-provider trait — see
`crates/stt-mlx/src/provider.rs:5–9`). Deepgram is naturally streaming, so the adapter:

1. **Lazy-connects** on first call (so `DeepgramAdapter::new()` doesn't bind a socket
   ahead of `start meeting`).
2. **Encodes** the chunk's `Vec<f32>` to little-endian i16 PCM and sends as one binary frame.
3. **Drains** any text frames currently buffered on the socket using a short read timeout
   (default 50 ms, configurable via `read_drain_timeout`); for each `Results` envelope with
   `is_final = true`, build an `SttSegment` and push to the result vector.
4. **Returns** the drained vector. Many calls return `vec![]` (Deepgram batches across
   chunks); a later call returns one or more segments accumulated since the last call.

**Timestamp policy**: Deepgram's `start` field is offset from when *Deepgram* started
receiving audio (= our first chunk send). The adapter records the first chunk's `ts_ms` as
`session_base_ts_ms`; subsequent segment timestamps are
`session_base_ts_ms + Deepgram.start * 1000`. Best-effort heuristic — within ~200 ms on
localhost, perfectly fine for the question-detector pipeline which only reads finalized
text strings (`shared/types.ts:TranscriptChunk.text`), not millisecond-accurate boundaries.

## API-Key Handling

`DEEPGRAM_API_KEY` is read via `env::var()` in `DeepgramConfig::default()`. The variable is
never logged, never written to disk, never sent to telemetry (telemetry comes in T-3.9 with
explicit privacy assertions). Callers may override via `DeepgramConfig::api_key` for testing.
The key is sent only over the WebSocket upgrade `Authorization` header — the same wire
contract Deepgram documents.

`bridge_acknowledge`-equivalent logging in `helper-daemon` (when integrated) MUST NOT log
the key; T-3.9 telemetry test will assert this with an explicit grep.
