## Privacy audit (R-3.6-2)

Goal: assert API keys NEVER appear in any code path that emits to telemetry, console, or future log surfaces.

- `src/store/settingsStore.ts` — `apiKeys` lives only in the in-memory store + the `localStorage` payload. No `console.*` calls anywhere in the file (grep clean).
- `src/components/SettingsSheet.tsx` — no `console.*` calls; the API-key input renders `type="password"` by default; the "Show" checkbox toggles to `type="text"` only on explicit user action and resets to hidden whenever the picker changes (`useEffect` on `sttProvider` resets `showKey = false`).
- `src/settings/testConnection.ts` — the default stub composes status messages from `labelFor(provider)` + provider name + the env var literal — **never** the API key value itself. Live impl (deferred to T-3.10) MUST follow the same rule; this is documented in the file header comment.
- The pill `message` field is the human-readable status the adapter returns; it is NOT the key. The component echoes whatever the (test-injected) `TestConnectionFn` returns — the contract is documented in `testConnection.ts` and tested via SH-U5/U6 with curated mock messages.
- T-3.9 will add a grep-test gating `apiKeys` and the per-provider env-var names against the telemetry log surface. That guard is owed but not yet shipped.

**Conclusion:** T-3.6 introduces no leak path. The follow-up enforcement (telemetry grep) is correctly scheduled in T-3.9, not T-3.6.
