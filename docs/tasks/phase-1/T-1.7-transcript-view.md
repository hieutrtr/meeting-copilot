# T-1.7 — React TranscriptView component

> Reference: `docs/IMPLEMENTATION-PLAN.md` Phase 1 raw T-1.3 ("Transcript view UI"); `docs/ARCHITECTURE.md` §8.2 (3-panel layout — transcript main, auto-scroll, search); `docs/PRD.md` §7.1 (wireframe — timestamped lines, search affordance, scroll counter).

## Acceptance Criteria (verbatim from INDEX)

> **T-1.7** — React `TranscriptView` component (virtualized list, auto-scroll, search input). **AC:** Vitest + Testing Library: render with 50 chunks, last chunk visible; type in search → matched chunks highlighted. Dep: T-1.1.

Decomposed:

- **AC-1** Component is a pure props-in / DOM-out function: `TranscriptView({ chunks })` (no `useTranscriptStream` call inside — testability + reuse from T-1.13 fixture E2E).
- **AC-2** Render with 50 sequential chunks → last chunk's text is in the document and visible (`scrollIntoView` called on last item or container scrolled to bottom).
- **AC-3** When new chunks are appended (props change), the view auto-scrolls so the newly-added last chunk is visible.
- **AC-4** Search input: typing a query filters the displayed list to chunks whose `text` contains the query (case-insensitive); the matched substring is wrapped in a `<mark>` element so it renders highlighted.
- **AC-5** Empty-search behavior: query empty → all chunks shown, nothing highlighted, list scrolls to bottom.
- **AC-6** Each chunk renders a stable timestamp affordance (formatted `mm:ss` from `startTs` ms) so the wireframe's `[00:12:01]` style is reachable in T-1.9 styling.
- **AC-7** Virtualization budget — at 50 chunks every test passes; the implementation must handle 1000+ chunks without rendering all of them. We satisfy this with windowed rendering: render only the slice intersecting the visible viewport plus a small over-render. **Soft AC** — vitest verifies it does NOT render all 1000 `<li>` elements (DOM count < chunks.length / 5) when the list is scrolled near the bottom.
- **AC-8** No external runtime dep on `react-window` / `react-virtuoso`. We implement a minimal windowing primitive in-tree (≈40 lines: fixed-row-height assumption + `scrollTop` math + over-render constant). Reason: those libs require `ResizeObserver` polyfills under jsdom and add bundle weight Phase 1 doesn't need — three-card lists in PRD §7.1 are the production size, not 100k.

## TDD plan

Test runner: **Vitest + `@testing-library/react` + jsdom**. The repo's vitest config currently uses `environment: "node"` — T-1.7 adds an opt-in jsdom environment for component tests via `// @vitest-environment jsdom` per-file pragma (preferred over flipping the global env, which would re-baseline all 9 existing tests on a different host).

New deps (devDependencies):

- `@testing-library/react` — render + queries
- `@testing-library/jest-dom` — `toBeInTheDocument`, `toHaveTextContent`
- `@testing-library/user-event` — typing into search input
- `jsdom` — DOM environment

Tests authored RED-first in `src/components/TranscriptView.test.tsx`:

| ID | Case | Asserts |
|---|---|---|
| **UI-T1** | renders all chunks with their text + formatted timestamp | each `[mm:ss]` prefix present; first + last chunk text in document |
| **UI-T2** | with 50 chunks, last chunk is in the document and `scrollIntoView` was called on the container/last row after mount | mock `Element.prototype.scrollIntoView` (jsdom doesn't implement it) and assert call count ≥ 1 |
| **UI-T3** | appending a new chunk via re-render scrolls to the new last chunk | rerender with `[…chunks, newChunk]`; new chunk in DOM; `scrollIntoView` called again |
| **UI-T4** | search input filters list — only matching chunks remain | type query, assert hidden chunks gone; re-empty input restores list |
| **UI-T5** | search highlights match — `<mark>` element wraps the queried substring inside matching chunks | type "alpha"; chunk text "say alpha now" → `<mark>alpha</mark>` present and case-insensitive ("AlPhA" same hit) |
| **UI-T6** | virtualization soft-cap: with 1000 chunks, rendered `<li>` count is < 100 | assert `screen.queryAllByRole("listitem").length < 100` after scroll near bottom |

UI-T6 covers AC-7. UI-T1+UI-T2 cover AC-2/AC-6. UI-T3 covers AC-3. UI-T4+UI-T5 cover AC-4/AC-5.

`scrollIntoView` mock pattern: in `beforeAll`, set `Element.prototype.scrollIntoView = vi.fn()` (jsdom v23+ leaves it undefined). Reset spy between tests.

## Risk + Mitigation

| Risk | Likelihood | Mitigation |
|---|---|---|
| Adding jsdom shifts all existing vitest cases off node env and silently changes behavior. | M | Use `// @vitest-environment jsdom` pragma on the new test file only — keep `vitest.config.ts` `environment: "node"` so the 9 existing cases stay byte-identical. |
| `scrollIntoView` polyfill leaks between tests. | L | Reset via `vi.clearAllMocks()` in `beforeEach` + restore the original (undefined) descriptor in `afterAll`. |
| In-house virtualization drifts from production needs (variable row height once T-1.9 adds "?" hover button). | M | Document the fixed-row assumption inline; T-1.9 review checks if a real library is needed once interactive rows ship. **For the loop's MVP exit gate (1-meeting smoke), 50 chunks is the realistic upper bound — virtualization is over-spec for the demo.** |
| `<mark>` matching with substring could break on regex special chars in user query. | L | Use case-insensitive `String.prototype.toLowerCase()` + `indexOf`, never `RegExp` constructed from user input. |
| Testing Library's `userEvent.type` is async — flaky if not awaited. | L | Always `await user.type(...)`; vitest's `it` already awaits async fn. |
| Including jsdom + RTL bumps install time / bun.lock churn. | L | Acceptable Phase 1 cost; T-1.8 / T-1.9 / T-1.11 all reuse the same harness. Pin majors only — `^16` for RTL, `^25` for jsdom. |

## Hardware-blocked verification

None — this is a pure DOM/React task. All 6 tests run in the loop sandbox under vitest+jsdom. Re-run after install on user's host: same `bun run test` command.
