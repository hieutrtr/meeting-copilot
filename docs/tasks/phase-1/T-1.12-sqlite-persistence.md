## Acceptance Criteria (verbatim from INDEX)

> **T-1.12** — Local persistence: SQLite via `tauri-plugin-sql` (or `rusqlite` if plugin install blocked). Schema: `Meeting`, `TranscriptChunk`, `Question`, `Answer`, `ContextSource` (per ARCH §10). **AC:** integration test: create meeting → insert 10 chunks + 1 Q/A → close DB → reopen → all rows present.

### Stack pick — `rusqlite` (Rust-side `Repo`), not `tauri-plugin-sql`

Both options are listed in the plan. Pick `rusqlite` because:

1. **Tests are cargo-side**: INDEX §"TDD per task" literally says `cargo test SQL integration (in-memory :memory: SQLite)`. `tauri-plugin-sql` would push the integration test into a Vitest+Tauri-IPC mock, which only proves the JS shim works — not the schema DDL.
2. **Daemon owns the DB per ARCH §10** ("Storage: SQLite ~/.claude-bridge/meetings.db, drizzle schema. WAL mode để daemon + UI write song song."). The daemon is Rust; the natural home for the schema + connection pool is `crates/helper-daemon`. The plugin variant would have moved DDL ownership into `src-tauri`'s frontend bridge.
3. **No system-libsqlite3 dependency** — `rusqlite` ships a bundled feature that compiles a vendored SQLite (`features = ["bundled"]`). Build environment has no extra setup burden vs the plugin's runtime requirement.
4. **Plain Rust integration test runs deterministic** — `Repo::open(tempfile)` → mutate → drop → re-open is the AC's exact shape. No async runtime, no Tauri test feature, no JS event loop.

`tauri-plugin-sql` re-enters the picture in Phase 1.x **if** the React side wants to query the DB directly (e.g. a "Past meetings" sidebar). Phase 1 demo runs everything through the daemon, so the plugin is dead weight for now. Documented in the deferral list below.

### Decomposed AC

- **AC-1** Public surface: `helper_daemon::repo` module exporting `Repo`, `RepoError`, plus DTO row structs (`MeetingRow`, `TranscriptChunkRow`, `QuestionRow`, `AnswerRow`, `ContextSourceRow`) that mirror `shared/types.ts` field names via `serde(rename_all = "camelCase")` for the eventual Tauri command return shape.
- **AC-2** `Repo::open<P: AsRef<Path>>(path: P) -> Result<Repo, RepoError>` opens (creating if absent) a SQLite database at the given path, runs schema DDL idempotently, and enables `journal_mode = WAL` + `foreign_keys = ON`. `Repo::open_in_memory()` returns a `:memory:`-backed instance for unit tests that don't need disk round-trip semantics.
- **AC-3** Schema DDL (idempotent — `CREATE TABLE IF NOT EXISTS`) creates exactly five tables + one junction:
  - `meetings(id PK, title, started_at, ended_at NULL, stt_provider NULL, model NULL, privacy_mode NULL, status)`
  - `transcript_chunks(id PK, meeting_id FK, text, start_ts, end_ts, is_final, speaker NULL, confidence NULL)`
  - `questions(id PK, meeting_id FK, text, detected_ts, method, confidence NULL, status NULL)`
  - `answers(id PK, question_id FK UNIQUE, text, generated_at, model, tokens_in NULL, tokens_out NULL, cached_ratio NULL)`
  - `context_sources(id PK, path, char_count, estimated_tokens, loaded_at)`
  - `meeting_context(meeting_id FK, context_id FK, PRIMARY KEY (meeting_id, context_id))`
  - All FKs declared `ON DELETE CASCADE` — Phase 1 doesn't expose meeting deletion in UI but the constraint is the right default; reviewers can wipe the file directly.
  - The `answers.question_id` is `UNIQUE` because `QAEntry` in `shared/types.ts` enforces 1:1 (an answer belongs to exactly one question).
- **AC-4** Insert API — six idempotent-on-conflict-error inserters (caller chooses to handle the error or trust UUID uniqueness):
  - `insert_meeting(&self, &MeetingRow) -> Result<(), RepoError>`
  - `insert_transcript_chunk(&self, &TranscriptChunkRow)`
  - `insert_question(&self, &QuestionRow)`
  - `insert_answer(&self, &AnswerRow)`
  - `insert_context_source(&self, &ContextSourceRow)`
  - `link_context_to_meeting(&self, meeting_id: &str, context_id: &str)`
- **AC-5** Read API — minimum surface T-1.13 needs to render a "past meeting" view:
  - `list_meetings(&self) -> Result<Vec<MeetingRow>, RepoError>` ordered `started_at DESC`
  - `get_meeting(&self, id: &str) -> Result<Option<MeetingRow>, RepoError>`
  - `list_chunks(&self, meeting_id: &str) -> Result<Vec<TranscriptChunkRow>, RepoError>` ordered `start_ts ASC`
  - `list_questions(&self, meeting_id: &str) -> Result<Vec<QuestionRow>, RepoError>` ordered `detected_ts ASC`
  - `get_answer(&self, question_id: &str) -> Result<Option<AnswerRow>, RepoError>`
- **AC-6** **The headline AC** — round-trip across `Repo` lifecycles. Test creates a temp file path, opens a Repo, inserts (1 meeting, 1 context source + link, 10 transcript chunks, 1 question + 1 answer), drops the Repo, re-opens at the same path, asserts every row is present and every field round-trips byte-for-byte. WAL files (`.db-wal` / `.db-shm`) are also cleaned up by the temp-file drop guard.
- **AC-7** Foreign key enforcement: inserting a chunk with a `meeting_id` that doesn't exist returns `RepoError::Sqlite(...)`. Test asserts the kind (`SqliteFailure(_, Some(ref msg))` containing `"FOREIGN KEY"`).
- **AC-8** Duplicate-PK rejection: inserting a meeting twice with the same id returns a constraint error.
- **AC-9** Serde camelCase parity — `serde_json::to_value(&MeetingRow { ... })` produces keys `id`, `title`, `startedAt`, `endedAt`, `sttProvider`, `model`, `privacyMode`, `status` (matches `shared/types.ts:MeetingSession`). Same parity check on `TranscriptChunkRow` (→ `meetingId`, `startTs`, `endTs`, `isFinal`), `QuestionRow` (→ `meetingId`, `detectedTs`), `AnswerRow` (→ `questionId`, `generatedAt`, `tokensIn`, `tokensOut`, `cachedRatio`), `ContextSourceRow` (→ `charCount`, `estimatedTokens`, `loadedAt`).
- **AC-10** No `rusqlite::Result::unwrap()` reachable from public API. All errors flow through `RepoError` (a `thiserror`-derived enum wrapping `rusqlite::Error` + `std::io::Error`). Public methods return `Result<_, RepoError>`.

### Out-of-scope (deferred — captured here so the review can flag them as not-regressions)

- Tauri command bindings (e.g. `#[tauri::command] fn save_meeting(...)`) — T-1.13 owns the IPC surface because it's the consumer that actually drives Stop→persist + reload→hydrate. Per ARCH §10, the daemon is the DB owner; the IPC commands are thin adapters.
- React side — no `src/store/persistenceStore.ts` lands this task. The hydrate flow is T-1.13's wiring; no UI changes here keep the test surface tight.
- Schema migrations / version table — Phase 1 ships v1 only; first migration lands when Phase 1.x adds e.g. a `tags` column. The DDL today uses `CREATE TABLE IF NOT EXISTS` so re-opening an older file is a no-op (it just doesn't get the new column — that's the point of v2's first migration).
- Encryption-at-rest — Phase 1 demo is local-only on the user's macOS user account. ARCH §11 ("Privacy Modes") puts encrypted-at-rest into Phase 2 hardening.
- `tauri-plugin-sql` JS bindings + drizzle codegen — Phase 1.x. The Repo's row DTOs already serialize as the right JSON shape (AC-9), so a future plugin/drizzle adapter can layer on top without re-shaping the types.
- Live mic capture wiring — T-1.13. This task ships the storage layer the wiring will call.

## TDD plan

Test runner: `cargo test -p helper-daemon` (the same crate the schema lives in). Tests file: `crates/helper-daemon/src/repo.rs` `#[cfg(test)] mod tests` (mirrors the in-tree test convention used by `bridge.rs` + `context.rs`).

Helpers (private to the test module):
- `TmpDb { path: PathBuf, _guard: () }` — wraps a unique temp-file path under `std::env::temp_dir()`, derived from `std::process::id() + atomic counter` (same pattern as `context.rs:TmpFile`). Drop removes the `.db`, `.db-wal`, and `.db-shm` siblings to leave the temp dir clean.
- `sample_meeting(id: &str) -> MeetingRow`, `sample_chunk(meeting: &str, idx: u32) -> TranscriptChunkRow`, `sample_question(meeting: &str) -> QuestionRow`, `sample_answer(question: &str) -> AnswerRow`, `sample_context() -> ContextSourceRow` — fixture builders so each test reads top-down without inline-construct noise.

Tests authored RED-first:

| ID | Layer | Case | Asserts |
|---|---|---|---|
| **DB-R1** | repo | `open` creates schema | After `Repo::open(tmp.path)`, querying `SELECT name FROM sqlite_schema WHERE type='table'` returns at least `meetings`, `transcript_chunks`, `questions`, `answers`, `context_sources`, `meeting_context`. |
| **DB-R2** | repo | `open` enables WAL + FK | `PRAGMA journal_mode` returns `"wal"`. `PRAGMA foreign_keys` returns `1`. Skipped on `:memory:` for journal_mode (SQLite forces `memory` mode there). |
| **DB-R3** | repo | meeting insert + readback | `insert_meeting(&m)` then `get_meeting(&m.id)` returns `Some(m_eq)` where every field matches byte-for-byte. NULL-able fields preserve `None`. |
| **DB-R4** | repo | chunk insert + ordered list | Insert 10 chunks with `start_ts = idx * 1000`; `list_chunks(meeting_id)` returns 10 rows in `start_ts ASC` order regardless of insert order (test inserts shuffled). |
| **DB-R5** | repo | question + answer 1:1 | Insert question + answer; `list_questions(meeting)` returns the question; `get_answer(question.id)` returns the answer; `get_answer("bogus")` returns `Ok(None)`. |
| **DB-R6** | repo | context source + link | Insert context source; `link_context_to_meeting(m, c)`; second link with same pair is a no-op (`INSERT OR IGNORE` semantics) and does not error. |
| **DB-R7** | repo | **AC-6 round-trip** | TmpDb path; open Repo; insert 1 meeting + 1 context source + link + 10 chunks + 1 Q + 1 A; **drop Repo**; **re-open same path**; every row present + field-equal. |
| **DB-R8** | repo | FK reject on orphan chunk | Insert chunk with `meeting_id = "ghost"` → `Err(RepoError::Sqlite(_))` whose stringified form contains `"FOREIGN KEY"`. |
| **DB-R9** | repo | duplicate PK reject | Insert same `MeetingRow` twice → second call returns `Err(RepoError::Sqlite(_))` containing `"UNIQUE"` (or `"PRIMARY KEY"`). |
| **DB-R10** | repo | answer per question UNIQUE | Insert 2 different `AnswerRow`s with the same `question_id` → second errors on the `UNIQUE` constraint. (Phase 2 may relax this if regenerate-answer ships; today the `QAEntry` model is 1:1.) |
| **DB-R11** | repo | serde camelCase parity | Round-trip `MeetingRow`/`TranscriptChunkRow`/`QuestionRow`/`AnswerRow`/`ContextSourceRow` through `serde_json::to_value(&row)` and assert the keys match `shared/types.ts` (e.g. `startedAt`, not `started_at`). Mirrors the parity check `bridge.rs::TranscriptChunkEvent` already does. |
| **DB-R12** | repo | empty queries return empty vec | `list_meetings()` on a fresh Repo → `Ok(vec![])`. `list_chunks("ghost")` → `Ok(vec![])`. No `unwrap()` panic on missing rows. |
| **DB-R13** | repo | re-open is idempotent on schema | `Repo::open(path)` twice on the same file does not error or re-error on `CREATE TABLE` (the `IF NOT EXISTS` clause is the regression gate). |

DB-R1..R13 cover AC-1..AC-10. AC-9 is DB-R11. AC-10 (no `unwrap()`) is enforced by `cargo clippy -- -D clippy::unwrap_used` if/when the project tightens lints; for this task it's enforced by code review (the DB-R12 case in particular flushes out any lurking `unwrap()` on `Option`).

## Risk + Mitigation

| Risk | Likelihood | Mitigation |
|---|---|---|
| `rusqlite` with `bundled` feature requires a C compiler in the build environment. | L | macOS dev hosts already have `cc` from Xcode CLT (already a Tauri 2 prerequisite per Phase 0 T-0.8). CI runners (when they exist Phase 2) install `cc` as part of standard rust toolchains. No new install gate vs Phase 0. |
| WAL files leak in test temp dirs (`.db-wal`, `.db-shm`) when `Repo::open` panics mid-test. | L | `TmpDb::Drop` removes all three siblings (`.db`, `.db-wal`, `.db-shm`) and ignores `NotFound`. `Repo::open` never `panic!`s — it returns `Err(RepoError::...)`; the test's `expect()` is the only panic point and it lives after Repo construction so the temp file already exists and Drop will clean it. |
| Multi-thread `Connection` use without `Mutex` — a future T-1.13 caller might share `Repo` across the meeting pump thread + the Tauri command thread. | M | `Repo` wraps `Connection` in a `std::sync::Mutex` and exposes `&self` methods. `rusqlite::Connection` is `!Sync` by default; the Mutex is the `rusqlite`-blessed pattern (per the rusqlite README "Concurrency" section). All public methods take `&self` so the Mutex is internal. |
| FK `ON DELETE CASCADE` accidentally wipes data if a future migration drops a parent row. | L | Phase 1 has no row deletion in any code path (UI doesn't expose it, daemon doesn't either). The CASCADE clause is defensive for Phase 1.x's eventual "delete meeting" feature. |
| Schema drift between `shared/types.ts` field names and Rust DTO field names → camelCase mismatch in JSON. | M | DB-R11 is the regression gate. The DTOs use `serde(rename_all = "camelCase")` (same convention as `bridge.rs:TranscriptChunkEvent` → `meetingId`, `startTs`). One-line break if a future contributor renames a field on either side. |
| Big transcripts (1000+ chunks) cause N+1 select on `list_chunks`. | L | Single-table `SELECT * FROM transcript_chunks WHERE meeting_id = ? ORDER BY start_ts` is one query, not N+1. SQLite handles 10k rows in <1ms on M1; `transcript_chunks(meeting_id, start_ts)` will get a covering index in Phase 1.x if the query plan needs it. |
| `cached_ratio` stored as REAL loses precision on round-trip. | L | SQLite REAL is IEEE 754 double; the `cacheReadRatio` in `pricing.ts` is also a double. Round-trip through SQLite is bit-identical (assuming no NaN) — no precision concern. NaN is rejected by `pricing.ts` already (NaN if `total === 0` in `cacheReadRatio` — guarded by the early-return). |
| `:memory:` tests can't validate WAL pragma (mode is forced to `"memory"`). | L | DB-R2 splits into two sub-asserts: `journal_mode == "wal"` only on file-backed Repos. `:memory:` Repos still validate `foreign_keys == 1`. |
| Concurrent `Repo` opens of the same file produce SQLITE_BUSY. | L | Phase 1 demo runs only one Repo per process. WAL mode permits concurrent readers + a single writer; T-1.13's pump is single-writer. Phase 1.x adds explicit `busy_timeout` if multi-process scenarios emerge (e.g. menubar app + main app). |
| Tests panic with "database is locked" on a slow CI runner. | L | Each test owns a unique temp-file (atomic counter + pid suffix). No shared state. |
| `serde_json::Value` round-trip on `f32`/`f64` in `confidence`/`cachedRatio` produces `null` if the value is `None`. | L | Expected — DB-R11 asserts `Some(0.95) → Number`, `None → Null` is the desired JSON shape (`shared/types.ts` says `confidence?: number`, so `undefined`/`null` parity is fine). |
