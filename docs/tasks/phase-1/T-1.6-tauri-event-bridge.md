## Goal

Glue the Phase 1 audio→STT pipeline (T-1.3 → T-1.4 → T-1.5) to the React UI by adding the **fourth quarter of the loop**: a Tauri-side event bus that emits two events:

1. **`transcript:chunk`** — fires every time the bridge drains a `Chunker` window, transcribes it via the active `SttProvider`, and produces one or more `SttSegment`s. Payload shape mirrors `shared/types.ts:TranscriptChunk` byte-for-byte (camelCase keys, `meetingId` + `id` injected by the bridge, `confidence` optional).
2. **`meeting:state`** — fires when the meeting state machine (T-1.9 owns it; this task ships the seam) transitions between `idle | active | ended`. Payload mirrors `shared/types.ts:MeetingStatus` plus `meetingId` and `atTs`.

The bridge is split across three crates so the test pyramid stays narrow:

- **`crates/helper-daemon/src/bridge.rs`** — defines `EventSink` trait + `EventBridge` pump (Tauri-free; testable via in-process `RecorderSink` that captures into a `Mutex<Vec<…>>`). This is where ~80% of the logic lives, and where ~80% of the tests live.
- **`src-tauri/src/lib.rs`** — adds a thin `TauriEventSink` wrapping `AppHandle` (delegates `emit_transcript_chunk` → `app.emit("transcript:chunk", …)`). One unit test ensures it constructs and emits without panic via `tauri::test::mock_app()`.
- **`src/hooks/useTranscriptStream.ts`** — React hook that subscribes via `@tauri-apps/api/event` `listen()`, accumulates `TranscriptChunk`s into state, returns `{ chunks, clear }`. Plus a sibling `subscribeTranscriptStream(handler)` plain function that the Vitest harness drives directly (no DOM dep).

### Why a `EventSink` trait, not a direct `AppHandle` borrow?

Three reasons:

- **Test determinism** — the `Chunker → SttProvider → emit` loop is the most regression-prone seam in the phase (timestamps, segment ordering, `is_final` propagation). Driving it against a `RecorderSink` lets us assert the full event sequence with zero IPC.
- **Phase 1.x prep** — out-of-process RPC (ARCH §8.2: Unix socket) is deferred. When it lands, the same `EventBridge` swaps the sink to a `WebSocketSink`. Provider stays unchanged.
- **No tokio churn in helper-daemon** — `AppHandle::emit` is sync; the trait is sync. T-1.9's state machine will be the first thing to introduce tokio (when the live `MicSource → Chunker → SttProvider` pump runs on a `spawn_blocking` worker).

### Why two events, not one merged?

Different consumers, different cadences. `TranscriptView` renders every chunk (10–30/min). `Start/Stop` button + meeting timer only care about state transitions (3–5/meeting). Splitting them keeps the React hook for transcript fast (no filtering) and the state hook for UI controls cheap. This mirrors ARCH §9.3 RPC `subscribe(meetingId)` shape (transcript / question / answer events as parallel streams).

### Why event names use `:` separator?

Tauri convention (and the existing `claude-bridge` event naming). Front-end listener: `await listen<TranscriptChunk>("transcript:chunk", e => …)`. The `:` is a literal character — Tauri does not interpret it as a namespace.

### Test fixture strategy

- `bridge.rs` tests use `audio_capture::Chunker::default()` + `stt_mlx::FakeStt::new("Hello world.")` so the produced text is deterministic.
- The chunker math (already verified in T-1.4): 80 000 samples @ 16 kHz / 32 000 samples-per-window = 2.5 windows → 2 full `PcmChunk`s @ ts_ms 0 + 2_000.
- Fake STT emits 1 segment per chunk → 2 events per `pump_one(80k samples)` call.
- The canonical JSON fixture is the **same literal** read by Rust serialise-equality + TS schema-parity tests. If the schema drifts on either side, both tests fail.

## Risk + Mitigation

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Tauri's `app.emit` is sync but expensive on large payloads (~ms per emit at 1 KB) | Medium | Medium | Phase 1 emits ≤ 30 chunks/min @ ~200 B each; total < 6 KB/min — well under any UI-latency concern. ARCH §11 budget allows 500 ms partial; emit overhead is < 1 ms. |
| `serde(rename_all = "camelCase")` mis-renames a field, breaks TS consumer | Medium | High | AC-9 #4 (canonical JSON parity) catches drift on the Rust side; AC-8 TS-T3 catches drift on the TS side. Both reference the same `shared/fixtures/transcript_chunk.sample.json` literal. |
| `EventBridge::pump_one` blocks the calling thread (real `MlxWhisperSubprocess` is ~120 ms/chunk) | High (in T-1.9) | Medium | Trait is sync by design; T-1.9 will run pump_one on a `tokio::task::spawn_blocking` worker so the UI thread stays responsive. Documented in T-1.5 review §"Streaming UI not blocking thread chính". |
| `tauri::test::mock_app()` API differs from runtime AppHandle (gating bug) | Medium | Low | The Tauri 2 docs specify `tauri::test::mock_app()` returns a real AppHandle. If the test fails on hardware, mark `#[ignore]` with documented re-run; the trait abstraction means the production wiring is unaffected. |
| React hook's `useEffect` cleanup loses unlisten handle on rapid re-render | Low | Medium | Hook stores the unlisten via a `useRef`; cleanup function awaits the listen promise, calls unlisten. Test TS-T2 verifies the unlisten function is callable + idempotent. |
| `confidence: Some(1.0)` serialises to `"confidence":1` (i64) on some serde_json versions | Low | High | f32 → JSON Number → serde_json renders `1.0` (with decimal) for f32/f64 sources. The parity test (AC-9 #4) catches this regression. Pinned `serde_json = "1"` (workspace already uses 1.0.x). |
| Rust `MeetingStatus::Display` "idle" string drifts from TS `MeetingStatus = "idle" | "active" | "ended"` | Low | Medium | AC-9 #6 hard-codes the three exact strings. Test fails if anyone changes the Display impl. |
| `helper-daemon` adds path-dep on `stt-mlx` → circular dep risk if stt-mlx ever depends on helper-daemon | Low | Medium | `stt-mlx` deliberately depends only on `audio-capture` (per T-1.5 design — no upward dep). Documented in T-1.5 review. |

## Scope Guardrails (what this task does NOT do)

- ❌ The meeting state machine itself (`Idle → Active → Ended` transitions, side-effects, persistence) — T-1.9 owns it. T-1.6 ships the `MeetingStatus` enum + `emit_state()` seam so T-1.9 just consumes it.
- ❌ `start_meeting` / `stop_meeting` Tauri commands — T-1.9.
- ❌ Live mic → bridge wiring (the long-lived task that pumps `CpalMicSource → Chunker → EventBridge::pump_one`) — T-1.9 (Start Meeting) constructs that.
- ❌ React `TranscriptView` UI component (virtualized list, search) — T-1.7. T-1.6 ships the `useTranscriptStream` hook the view consumes.
- ❌ Tokio runtime in `helper-daemon` — `pump_one` is sync. T-1.9 introduces the runtime via `tokio::task::spawn_blocking`.
- ❌ Out-of-process daemon RPC (Unix socket, ARCH §8.2) — Phase 1.x. The `EventSink` trait is the future-proof seam.
- ❌ Question / answer events (`question:detected`, `answer:chunk`) — T-1.10 + T-1.11 add their own sinks/streams. T-1.6 limits scope to transcript + state.
- ❌ Persistence of emitted events — T-1.12 (SQLite) intercepts at the sink layer (a `PersistingSink` that writes-then-forwards) once schema lands.
