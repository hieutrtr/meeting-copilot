# T-4.8 — Discovery hook: read & auto-register in `~/.claude-bridge/config.json`

> Phase 4 critical-path companion to T-4.2 server boot. After this lands, the meeting-copilot MCP binary self-registers into the claude-bridge daemon's config the first time it runs, so the dashboard can list it next to `dashboards: []` without operator side-loading.

**ARCH refs:**
- `docs/ARCHITECTURE.md` §9.1 *Discovery* (lines 326–345) — defines `meeting_copilots: []` array + parity with `dashboards: []`.
- `claude-bridge/docs/web-dashboard/v2/ARCHITECTURE.md` §16 *Config Schema* (lines 273–306) — full top-level shape; `version: 1`, absolute paths only, no tilde expansion at read time.
- `claude-bridge/src/lib/dashboard-installer.ts` lines 318–338 — `readConfigJson` + `writeConfigJsonAtomic` reference impl (`writeFileSync` to `<config>.tmp.<pid>` then `renameSync`).

**Tool surface impact:** none. T-4.8 does NOT add or alter any of the 5 tool entries. It runs once during MCP server boot (`bin.ts → startStdioServer → registerSelfInBridgeConfig`) as a best-effort side-effect. If discovery fails, server still boots and stderr-logs the reason; the MCP tools remain reachable over stdio.

---

## 1. Goals

1. Read `$CLAUDE_BRIDGE_HOME/config.json` (default `~/.claude-bridge/config.json`).
2. Validate top-level shape with Zod, scoped to fields meeting-copilot cares about (`version`, `meeting_copilots[]`). Pass-through unknown keys (daemon, dashboards, channels, …) untouched on write.
3. If `meeting_copilots[]` lacks an entry whose `path` matches our binary, append one: `{ version, path, default, installed_at?, mcp_bin }`. If a matching entry exists, leave it (return `{ alreadyRegistered: true }`).
4. Idempotent: re-running on an already-registered config produces a no-op write (atomic write only when content actually changes).
5. Atomic write — `writeFileSync(<config>.tmp.<pid>)` → `renameSync(<config>)` — same pattern as `claude-bridge/src/lib/dashboard-installer.ts:writeConfigJsonAtomic`.
6. Refuse to operate if `config.version > 1` — return typed `ConfigSchemaUnsupported`. Refuse to operate if the JSON is corrupt or the schema is invalid — return typed `BridgeConfigInvalid`.

## 2. Non-goals

- **No GitHub release fetch** (Phase 4.x). The `version` and `installed_at` come from local state only.
- **No flipping `default: true` flags** on other entries. Meeting-copilot is a peer of `dashboards: []`, not a replacement.
- **No tilde expansion.** ARCH §16 binds: paths are absolute; if `mcp_bin` resolves to a tilde-prefixed path we expand it before write so the persisted path is always absolute.
- **No daemon RPC.** Discovery is a pure file-system read + atomic write; daemon may be down.
- **No lockfile.** Atomic rename is good enough for a single-writer use-case (daemon writes via `dashboard-installer.ts`, MC writes via this module — keys are disjoint).

## 3. Schema (Zod, this loop)

`src/discovery/schema.ts`:

```ts
const MeetingCopilotEntrySchema = z.object({
  version: z.string().min(1),
  path: z.string().min(1),
  default: z.boolean().default(false),
  installed_at: z.string().optional(), // ISO 8601
  installed_from: z.string().optional(), // e.g. "github.com/anthropic/meeting-copilot@v1.0.0"
  mcp_bin: z.string().optional(),       // absolute path to bin.ts shim or compiled binary
}).passthrough();

const BridgeConfigSchema = z.object({
  version: z.number().int().min(1).default(1),
  meeting_copilots: z.array(MeetingCopilotEntrySchema).default([]),
}).passthrough();
```

`passthrough()` keeps unknown top-level keys (daemon, dashboards, channels, …) intact. We never strip them.

## 4. Public API (this loop)

`src/discovery/bridgeConfig.ts`:

```ts
export interface DiscoveryDeps {
  readFile?: (path: string) => string;     // throw on ENOENT
  exists?: (path: string) => boolean;
  writeFileAtomic?: (path: string, contents: string) => void;
  mkdirp?: (path: string) => void;
  homeDir?: () => string;
  bridgeHomeEnv?: string | undefined;      // override for CLAUDE_BRIDGE_HOME
  now?: () => Date;                         // installed_at clock
}

export interface RegisterOpts {
  version: string;       // pkg.version
  binPath: string;       // absolute path to MCP bin
  appPath?: string;      // absolute path to .app bundle, when known
}

export interface RegisterResult {
  configPath: string;
  alreadyRegistered: boolean;
  entry: MeetingCopilotEntry;
  warnings: string[];
}

export class ConfigSchemaUnsupportedError extends Error { code = "ConfigSchemaUnsupported"; }
export class BridgeConfigInvalidError extends Error { code = "BridgeConfigInvalid"; }

export function resolveBridgeHome(deps?: DiscoveryDeps): string;
export function readBridgeConfig(deps?: DiscoveryDeps): BridgeConfig;
export function registerMeetingCopilot(opts: RegisterOpts, deps?: DiscoveryDeps): RegisterResult;
```

Error codes (already in `src/mcp/tools.ts` `ERROR_CODES`):
- `ConfigSchemaUnsupported` — `config.version > 1`.
- `BridgeConfigInvalid` — corrupt JSON or schema violation.

## 5. Bootstrap wiring

`src/mcp/bin.ts` calls `registerMeetingCopilot()` BEFORE `startStdioServer()`. Failure is non-fatal: log to stderr and continue. This keeps the binary usable in environments without `~/.claude-bridge/` (e.g. CI runs of `bridge_meeting_install` against a sandbox).

Server-side `buildServer()` is unchanged — discovery has no MCP-protocol surface.

## 6. TDD plan

`src/discovery/bridgeConfig.test.ts` exercises 12+ cases via DI-injected fs:

1. Fresh — config absent → `mkdirp` + atomic write with `version: 1` and 1-entry `meeting_copilots[]`.
2. Existing config has `meeting_copilots: []` → entry appended, other top-level keys preserved (passthrough assertion on `daemon`, `dashboards`, `channels`).
3. Existing config has matching `path` entry → `alreadyRegistered: true`, no atomic write call (DI counter on `writeFileAtomic`).
4. Existing config has different-`path` entry → second entry appended (no de-dup by version, only by path).
5. Corrupt JSON → throws `BridgeConfigInvalidError` with original parse reason in `cause`.
6. `config.version: 2` → throws `ConfigSchemaUnsupportedError`.
7. `config.version: 0` → throws `BridgeConfigInvalidError` (Zod min(1)).
8. `meeting_copilots[].path` of wrong type (number) → throws `BridgeConfigInvalidError`.
9. `CLAUDE_BRIDGE_HOME=/tmp/foo` env override → resolves to `/tmp/foo/config.json` (no tilde expansion).
10. `CLAUDE_BRIDGE_HOME=~/foo` literal-tilde override → rejected with `BridgeConfigInvalidError` (per ARCH §16: absolute paths only).
11. `CLAUDE_BRIDGE_HOME` containing `..` segments → rejected (path-traversal sanity).
12. Atomic write → `writeFileAtomic` invoked exactly once per non-no-op call; on retry without state change, zero invocations.
13. `installed_at` deterministic via injected `now()`; format `YYYY-MM-DDTHH:mm:ss.sssZ`.
14. `binPath` containing tilde — expanded to `homeDir() + path.slice(1)` BEFORE write (persisted value is absolute).

## 7. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Schema drift if claude-bridge bumps `config.version` past 1 | `ConfigSchemaUnsupported` — operator must upgrade meeting-copilot before claude-bridge daemon. |
| Two MC processes racing on first boot | Atomic rename is single-step; second writer overwrites first's still-correct state (idempotent payload). |
| `passthrough()` accidentally drops a key on round-trip | Test #2 asserts `daemon` + `dashboards` keys survive a write. |
| Absolute-path violation | Tilde and `..` segments rejected up-front; tests #10/#11 cover. |
| Boot blocking on fs failure | Best-effort caller in bin.ts swallows + stderr-logs; server still starts. |
