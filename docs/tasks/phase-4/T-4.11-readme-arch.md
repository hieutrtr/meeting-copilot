## 3. Spec — `docs/ARCHITECTURE.md` Phase 4 addendum

### 3.1 Where each addendum block lands

The existing ARCH stays untouched. Each Phase 4 update block sits **after** the section it amends (or at the end, for §16 NEW), separated by a `---` divider, and starts with a verbatim header following the Phase-3-style pattern:

```
### 9.5 Phase 4 update — MCP server impl pointer (T-4.2..T-4.7)
```

**Three subsection blocks under §9 + one new top-level §16:**

1. **§9.5 Phase 4 update — MCP server impl pointer (T-4.2..T-4.7).** Documents:
   - Stdio MCP server binary at `src/mcp/bin.ts` (entrypoint), `src/mcp/server.ts` (`buildServer` + `startStdioServer`), `src/mcp/tools.ts` (5-tool Zod surface + closed `ERROR_CODES` set).
   - Handler modules under `src/mcp/handlers/` — `install.ts` (T-4.3), `start.ts` + `deeplink.ts` (T-4.4), `status.ts` (T-4.5), `stop.ts` (T-4.6), `export.ts` + `exporters/{markdown,json,vtt,srt}.ts` (T-4.7).
   - SDK pin: `@modelcontextprotocol/sdk ^1.0.0` (matches claude-bridge daemon `package.json` pin).
   - Error envelope: every handler returns `{isError: true, content: [{type:"text", text: "<ErrorCode>: <message>"}]}` where `<ErrorCode>` is one of the closed `ERROR_CODES` set in `src/mcp/tools.ts`. Adding a code requires updating that array AND the handler test (review-checkbox gated).
   - Telemetry hook: handlers emit through the existing opt-in `src/telemetry/telemetryLog.ts` sink (T-3.9). No transcript bytes; the scrubber's `FORBIDDEN_KEYS` audit ran in each T-4.<N>-review doc.
   - Run script: `bun run mcp-server` (uses `package.json#bin: meeting-copilot-mcp`).

2. **§9.6 Phase 4 update — Deeplink scheme + spawn safety (T-4.4).** Documents:
   - URL scheme `meeting-copilot://` declared in `src-tauri/tauri.conf.json` (`tauri-plugin-deep-link.desktop.schemes`).
   - Pure URL builder at `src/mcp/deeplink.ts` — `URLSearchParams` only, no string concat. 13 R-2 injection vectors tested in `src/mcp/deeplink.test.ts`.
   - Spawn invocation: `child_process.spawn("open", [deeplink], { shell: false })` — array argv, never shell string.
   - Two pre-spawn gates (BLOCKING per INDEX R-2 review checkbox):
     1. **Path-traversal guard** on `contextPaths` strings — `..` segments and absolute path traversal attempts rejected before any URL build.
     2. **Privacy mode gate** via `isSttProviderAllowed(privacyMode, sttProvider)` from `src/privacy/privacyMode.ts` — Local-first + Deepgram → `PrivacyModeViolation` typed envelope, spawn never invoked.
   - Cargo wiring + Tauri Info.plist verification deferred to host per `docs/tasks/phase-4/T-4.4-manual-verify-deeplink.md` (Phase 0 carry-forward — sandbox lacks Xcode CLT).

3. **§9.7 Phase 4 update — Embed CORS + token TTL (T-4.9).** Documents:
   - Helper-daemon Axum router at `crates/helper-daemon/src/embed_http.rs` binds `127.0.0.1:7411`. Two routes: `GET /embed/transcript/:meetingId` (HTML shell) + `GET /embed/transcript/:meetingId/events` (SSE).
   - **CORS allow-list = `http://127.0.0.1:7878` only** (claude-bridge dashboard default port). Hardcoded; no wildcard ever. Wildcard-veto + wrong-port test cases ship in `embed_http.rs` `#[tokio::test]` block.
   - **Auth = single-use UUID token** minted by helper daemon at `bridge_meeting_start` time, scoped to a single `meetingId`, **5-minute TTL**. Mint/verify in `crates/helper-daemon/src/auth.rs`; `Clock` dependency injected for deterministic TTL boundary tests (exact + 1ns).
   - **Headers on every response (200 / 401 / 403 paths):** `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Frame-Options: SAMEORIGIN`.
   - TS-side embed UI at `src/embed/TranscriptEmbed.tsx` + Vite entry `src/embed/transcript-entry.tsx` build into `dist/embed/transcript.html`. Mocked `EventSource` lifecycle test in `src/embed/TranscriptEmbed.test.tsx`.
   - Live binding: helper-daemon binary entrypoint (consumes `EmbedState::register_channel` / `deregister_channel`) is **Phase 4.x deferred** — out-of-process binary lands when the operator sets up the launchd service; Rust tests today exercise the `Router` directly via `axum::ServiceExt::oneshot`.

4. **§16 Discovery — `~/.claude-bridge/config.json` (NEW, T-4.8).** Documents:
   - Source of truth for the schema slice: `src/discovery/schema.ts` (Zod). meeting-copilot owns the `meeting_copilots: []` array and the top-level `version: number` (rejects `> 1` with typed `ConfigSchemaUnsupported` error). All other top-level keys (`daemon`, `dashboards`, `channels`, …) preserved on round-trip via Zod `.passthrough()` because the daemon and meeting-copilot are concurrent writers of the same JSON file.
   - Per-entry shape (also `.passthrough()`): `{ version, path, default?, installed_at?, installed_from?, mcp_bin? }` plus arbitrary unknown keys.
   - Path conventions: tilde-prefixed and `..`-containing path inputs rejected with `BridgeConfigInvalid` (no tilde expansion — absolute paths only, mirroring the daemon's dashboard-installer).
   - **Atomic write** (T-4.8 implementation `src/discovery/bridgeConfig.ts`): `writeFileSync(<config>.tmp, …)` then `renameSync(.tmp, .)` — same pattern as claude-bridge `dashboard-installer.ts`.
   - **Idempotency:** existing entry with matching `path` is updated in-place; the writer returns `{ alreadyRegistered: true }` and skips the file write entirely if no field changed. Re-register asserts file-write call count = 0 in the test gate.
   - **Env override:** `CLAUDE_BRIDGE_HOME` (default `~/.claude-bridge`); env-rooted paths must be absolute.
   - Boot-time hook: `src/mcp/bin.ts` wraps the registration call in `try/catch` so server boot never crashes on a discovery failure (a corrupt config logs the error and continues; production callers can still drive the MCP surface).

- Sub-section headers use the `### N.X Phase 4 update — <subject>` pattern (mirrors §3.4 / §4.1 / §11.1 from Phase 3).

A new top-level doc (sibling to ARCH, PRD, IMPLEMENTATION-PLAN, provider-comparison). Targets:

- **Audience:** Telegram operator + claude-bridge daemon implementor needing the exact JSON-RPC contract.
- **Length:** ~150–250 lines. Tool reference, not a tutorial.

### 5.1 Required sections

1. **Header + scope.** "What this doc is" / "What this doc is not" — one paragraph each. The source of truth note: `src/mcp/tools.ts` Zod schemas; this doc reflects that surface at sign-off time and may drift; the test gate is `src/mcp/tools.test.ts`.
2. **Tool surface table.** Columns: `Tool name | Handler file | Phase 4 task | Description (one line)`. Five rows verbatim from `TOOL_DEFINITIONS` in `src/mcp/tools.ts`.
3. **Closed error code set.** Table of `ERROR_CODES` (`NotImplemented`, `PrivacyModeViolation`, `DeeplinkNotRegistered`, `ContextNotFound`, `MeetingNotFound`, `InvalidMeetingId`, `ConfigSchemaUnsupported`, `BridgeConfigInvalid`) × {emitted-by-handler, meaning, sample message}. Pulled from `src/mcp/tools.ts` lines 42–51.
4. **Per-tool reference (×5).** One subsection each. Each subsection contains:
   - **Name + handler file** (relative path).
   - **Input schema** — JSONC pseudo-schema rendering the Zod definition (object keys, types, optional / required, allowed enum literals). Match `src/mcp/tools.ts` byte-for-byte modulo formatting.
   - **Output schema** — same treatment.
   - **Error envelopes** — list of `ErrorCode` values the handler can emit + when.
   - **Example invocation** — JSON-RPC body for the `tools/call` request + the `result.content[0].text` shape on success.
5. **Discovery quick-reference.** Pointer to `docs/ARCHITECTURE.md#16-discovery` + the same `~/.claude-bridge/config.json` snippet from the README, marked as "see ARCH §16 for canonical schema".
6. **Telemetry note.** One paragraph: every handler call emits a scrubbed `mcp_tool_invoked` / `mcp_tool_error` event through `src/telemetry/telemetryLog.ts` IFF `telemetryEnabled === true` (default off). No transcript bytes; allow-list-gated; cross-ref ARCH §14.
7. **References.** Cross-links to `docs/ARCHITECTURE.md` §9.5/§9.6/§9.7/§16, the per-task review docs (`T-4.2-review.md` … `T-4.10-review.md`), `src/mcp/tools.ts`, claude-bridge daemon `src/mcp/tools.ts` (reference impl).

### 5.2 Source-of-truth rule

Every tool / error code / enum literal in the doc MUST cite the implementation file/line where the Zod definition lives, **not** a fresh value the doc invents. If the docs and the code drift, the code wins; the doc breaks first (caught by manual review during the next phase or by the `bun run test src/mcp/tools.test.ts` snapshot check).
