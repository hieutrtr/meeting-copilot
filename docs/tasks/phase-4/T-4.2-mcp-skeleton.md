## 1. Goal

Stand up the MCP server **surface** for meeting-copilot — stdio transport, 5 tool stubs, Zod-typed input/output schemas. **No business logic** lands here: every handler returns the typed `not_implemented` envelope. T-4.3..T-4.7 fill them in one at a time.

This is the bulk of the Phase 4 file footprint (~600–800 LOC) precisely because it is skeleton-heavy: handler files, exporters, fixtures, and the `tools/list` snapshot all originate here. Subsequent tasks edit one handler at a time without touching the wiring.

## 5. TDD Plan

The skeleton is verified by a single integration test that boots the server through an in-memory `Duplex` pair (no real subprocess). The MCP SDK supports stdio transport built from an arbitrary readable/writable pair, so the test wires:

```
Client(InMemoryTransport_a) ↔ Pipe ↔ InMemoryTransport_b → Server
```

- `Client.listTools()` → assert 5 names, schema match.
- `Client.callTool({ name, arguments: {} })` for each → assert `isError: true` and the placeholder text shape.
- `Client.callTool({ name: "bogus", arguments: {} })` → assert error response.

Tests are **deterministic** — no real fs / network / process spawn. Mock-stdio is preferred over real `Bun.spawn` because the test doubles up as a doc — readers see the JSON-RPC framing inline.

A separate unit test against `src/mcp/tools.ts`:
- `zodToJsonSchema` round-trip per tool — input → JSON Schema → assert minimal-property-set is preserved.
- Closed error-code set is exported and frozen (`Object.freeze` assertion).

A regex test asserts the SDK + Zod pins in `package.json` (AC-4, AC-5).

## 6. Risks

| # | Risk | Mitigation |
|---|---|---|
| R-1 | **SDK API surface mismatch** between claude-bridge consumer (`Server` / `StdioServerTransport` / `ListToolsRequestSchema` / `CallToolRequestSchema`) and our MC provider — the daemon imports these from `@modelcontextprotocol/sdk/server/index.js` and `@modelcontextprotocol/sdk/server/stdio.js`. We do the same. | Pin same `^1.0.0` range. The mock-stdio test boots both a Client and a Server inline — if SDK API changes, the test fails compilation. |
| R-2 | **Zod-derived JSON Schema drift** between Vitest snapshot and downstream daemon expectations. | Use a single conversion path (`zod-to-json-schema` lib pinned at install time, or the SDK's own helper if exported); snapshot the conversion output in `tools.test.ts` so any drift is visible in PR diff. |
| R-3 | **Placeholder envelope shape diverges from real handler shape** in T-4.3..T-4.7. | The Zod schemas in `tools.ts` define both input *and* output. Placeholders return `{ isError: true }` only; real handlers will validate output against the same schema before returning. T-4.<N> reviews enforce this with a schema-validation assertion. |

## 7. Telemetry

The skeleton wires (but does **not** activate) the telemetry seam: each handler receives an injected `emit(event, payload)` callback (default `noop` in tests; T-3.9 `telemetryLog` adapter in production). T-4.3..T-4.7 use it to record `mcp_tool_invoked` / `mcp_tool_error`. The forbidden-key audit (`text`, `transcript`, etc.) lives in `src/telemetry/scrub.ts` already; no Phase 4 changes needed.
