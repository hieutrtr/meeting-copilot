## Implementation Notes

### Pure regex over a real XML parser

Apple's plist format is stable since 10.0 (2001). Adding an XML parser dep for one well-known key would add 10–50 KB of bundle and a parsing failure mode. The single-key regex tolerates compact and multi-line layouts (`infoPlist.test.ts` "handles compact" + "handles whitespace and newlines"), and graceful-fails to `null` on garbage input. T-4.3 §7 R-1 documents the contingency: future Apple drift surfaces as `installed: true, version: undefined` — the bundle is found, the version unknown, and the operator is told to reinstall.

### Three output states, not two

Spec §4.3 documents the third state explicitly: bundle directory exists but `Contents/Info.plist` lacks `CFBundleShortVersionString`. Distinguishing "missing" from "corrupt" matters because the operator's next action differs (install vs. reinstall). The fixture `Info.plist.missing-version.xml` exercises this branch; the handler emits `installed: true, message: /malformed/`.

### Output schema as a defense-in-depth gate

Every code path through `handleInstall` builds an `InstallOutput`-typed payload, then re-parses it through `InstallOutputSchema.parse()` before wrapping in the `ToolResult` envelope. If a future maintainer adds a field that doesn't appear in the schema, the parse fails and the dispatcher's try/catch surfaces a Zod error envelope rather than letting an off-spec payload escape on the wire. The cost is one extra Zod validation per call (sub-millisecond) — well worth it for an externally-visible MCP tool.

### Path resolution: 3-tier precedence

`args.path` (caller) → `deps.appBundlePath` (test/process override) → hardcoded `/Applications/Meeting Copilot.app`. No tilde expansion, no env-var substitution — the precedence is trivially auditable and tests pin all three tiers. This mirrors the dashboard ARCH §16 "absolute paths only" rule.

### `package.json` lookup at call time, with graceful fallback

`readPackageVersion()` walks up three directories from this file (`src/mcp/handlers` → repo root) and reads `package.json`. Wrapped in try/catch: any IO/JSON failure yields `"0.0.0"`. The handler is still callable from a packaged binary that may not include `package.json` adjacent — the message just shows `expectedVersion: "0.0.0"` instead of the real version. T-4.12 release packaging keeps `package.json` next to `dist/`. Tests inject `deps.packageVersion` directly (no fs side-effect during testing).

### server.test.ts integration test design choice

The integration test passes an explicit `path: "/var/empty/__t43_integration_meeting_copilot__.app"` so the test never reads the developer's real `/Applications/Meeting Copilot.app`. CI machines have no such bundle regardless, but the explicit path makes the test deterministic across all hosts.
