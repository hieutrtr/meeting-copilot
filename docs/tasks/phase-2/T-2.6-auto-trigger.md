## Scope (in)

1. New module **`src/queue/queueWorker.ts`** — pure JS state machine that:
   - Owns a single drain loop (`notify()` → microtask → `dequeue()` → `ask()` → fold deltas → `complete()` / `fail()` → recurse if pending).
   - Calls **`store.markAuto(...)`** at job-start so the question chip lands in the transcript before the answer arrives. Reuse the existing newest-first ordering of `useQuestionStore.questions[0]`.
   - Wraps `askClaude` (T-1.10) verbatim — no SDK shape changes — and forwards stream events (`delta` / `usage` / `stopReason`) to caller-supplied callbacks.
   - Tracks **first-token latency** (enqueue → first `delta`) and **end-to-end latency** (enqueue → final `done`) per item via injectable `now()`.
   - Single-flight: `queue.dequeue()` is the only transition into in-flight; never two `ask()`s concurrent.
2. New helper on **`src/store/questionStore.ts`** — `markAuto(text, opts)`. Mirrors `markFromChunks` shape but writes `method: "auto"` and optionally `confidence: HaikuVerdict.confidence`. Returns the new `Question`.
3. **Tests** — `src/queue/queueWorker.test.ts` (Vitest) covering structural behavior, single-flight invariant, error paths, latency measurement under fake timer, and `markAuto` integration. Plus `src/store/questionStore.test.ts` extension covering `markAuto`.

## Scope (out / deferred)

- **React hook surface (`useQueueWorker`)** — deferred to T-2.8 (UX) where the AnswerPanel is wired to the worker's stream events. T-2.6 ships only the framework-agnostic worker module + tests; App.tsx wiring is not modified in this task to keep diff narrow and Phase-1 behavior byte-identical.
- **Live SDK call** — covered by mocked-SDK tests + the existing live-call coverage in `claudeClient.test.ts` (T-1.10). PHASE-BROWSER-TEST.md will add a manual host-pass step under T-2.10.
- **Cancellation of in-flight `ask()`** — `useAskClaude` (T-1.11) owns request-id-gated cancellation in React. The worker's `stop()` only prevents *next* dequeue; mid-flight `ask()` runs to completion (its result is dropped if `stop()` was called). Aborting in-flight HTTP is a Phase-2.x concern (depends on `AbortController` plumbing through SDK).
- **Cost guard threshold** — T-2.7 reads `usage` events the worker forwards; the worker itself does not enforce cost limits.
- **Settings-driven max-depth / threshold** — T-2.9 wires `localStorage` slider into queue construction; T-2.6 takes the queue as an injected dep.
- **SQLite-backed persistence** — T-2.5 already shipped the adapter seam; no new persistence work here.

| AC-7 | **`stop()` prevents further dequeue** — calling `notify()` after `stop()` is a no-op; in-flight item completes naturally. | Test: enqueue 3 items, complete the first, call `stop()`, call `notify()`, assert `ask` was called exactly 1×. |

## TDD Plan (test cases, written before implementation)

### `src/queue/queueWorker.test.ts`

1. **Construction** — `createQueueWorker({ queue, ask, getContextDoc, store })` returns `{ notify, stop, isRunning }`. `isRunning()` initially `false`.
2. **Empty notify** — `notify()` on empty queue is a no-op (no `ask` call).
3. **Single item drain** — enqueue 1 → `notify()` → microtask flush → `ask` called once with `{ question: "what's the deadline?", contextDoc, recentTranscript }`.
4. **Marks question via store** — `store.markAuto` called once with `{ text, meetingId, confidence, detectedTs }` matching the queued item.
5. **Stream forwarding** — fake `ask` yields 3 deltas + 1 usage + 1 stopReason → `onItemDelta` fires 3×, `onItemDone` fires 1× with the final `AskClaudeResult`.
6. **`queue.complete` called on done** — worker calls `queue.complete(itemId)` after the generator returns.
7. **`queue.fail` called on error** — `ask` throws sync → `queue.fail(itemId, errorMsg)` called + `onItemError` fires.
8. **`queue.fail` called on mid-stream throw** — generator yields 1 delta then throws → `queue.fail` called + partial-text preserved on `onItemError`.
9. **Single-flight invariant** — enqueue 5, drive `notify()` once, assert in-flight count never exceeds 1 (track via `onItemStart` / `onItemDone` counter delta).
10. **Sequential drain** — 5 items processed in FIFO order; `onItemDone` order matches enqueue order.
11. **First-token latency** — fake clock advances 50 ms between enqueue and first delta; worker reports `firstTokenLatencyMs ≈ 50` to `onMetric`.
12. **End-to-end latency** — fake clock advances 200 ms total; worker reports `endToEndLatencyMs ≈ 200` to `onMetric`.
13. **Latency budget gate** — synthetic timing of (enqueue → 200 ms Haiku-equivalent → 2000 ms Sonnet first-token) → assert first-token < 10 000 ms (AC-1).
14. **Notify idempotence** — enqueue 1, call `notify()` 100×, assert `ask` called exactly 1× (AC-8).
15. **Stop semantics** — enqueue 3, drain 1, call `stop()`, call `notify()`, assert `ask` invocation count stays at 1 (AC-7).
16. **Stop is idempotent** — `stop()` then `stop()` again does not throw.
17. **Manual-mark independence** — direct `useQuestionStore.markFromChunks` call does NOT trigger the worker (`ask` count = 0). Worker only reacts to its own queue's `dequeue` → `ask` path. (AC-5)
18. **Empty queue post-drain** — after all items drained, `isBusy()` returns false, `notify()` is a no-op.
19. **Defensive null on no-context** — `getContextDoc` returns empty string → still passes through to `ask` as `""`; no crash.
20. **Recent-transcript getter is dynamic** — between item 1 and item 2 the transcript getter returns different strings; each `ask` invocation sees the snapshot at *its* call time, not enqueue time.
21. **Worker survives `markAuto` throw** — store throws → worker still calls `queue.fail` + emits error event (resilience).

### `src/store/questionStore.test.ts` (additions)

22. `markAuto("")` returns null + leaves list untouched.
23. `markAuto("what's the deadline?")` prepends a Question with `method: "auto"`, `status: "open"`, `text` verbatim.
24. `confidence` opt is propagated onto the Question (mirrors `HaikuVerdict.confidence`).
25. `meetingId` opt overrides store's active meetingId; falls back to "unknown" when neither is set.
26. `markFromChunks` then `markAuto` → both questions land newest-first in the list.

## Risk + Mitigation

| Risk | Probability | Impact | Mitigation |
|---|:---:|:---:|---|
| **Worker double-fires when both detector and manual-mark hit close together.** | Low | Medium | Manual mark never enters the queue (different code path); detector → dedup window (T-2.4) → queue (T-2.5) catches structural duplicates within 60 s. AC-5 test asserts the worker does not see `markFromChunks` calls. T-2.8 (UX) will surface the `method: "auto"` vs `"manual"` distinction in the AnswerPanel header so a user can never accidentally drive both at once. |
| **`ask` generator deadlocks on uncaught error mid-stream → worker stuck `isRunning: true` forever.** | Low | High | `ask()` is wrapped in `try/finally`; `queue.complete` or `queue.fail` is called in `finally`. Test 8 (mid-stream throw) asserts the worker proceeds to next item even after a throw. |
| **`notify()` recursion on tight successful drains overflows the call stack.** | Low | Medium | The drain loop awaits the `ask` generator's `Promise` chain — control yields to the event loop between iterations. Test 9 (single-flight under 5 items) implicitly covers this; no synchronous recursion path exists. |
| **First-token latency exceeds 10 s under real network conditions.** | Medium | Medium | AC-1 is a *simulated* gate (mocked SDK + fake timer). Live re-verify lands in PHASE-BROWSER-TEST.md (T-2.10 / sign-off) on Apple-Silicon hardware with `ANTHROPIC_API_KEY` set. The 10 s budget already includes a 7.7 s buffer over the proven 2.3 s warm-cache baseline (T-1.10 spike-memo). |
| **Worker's `markAuto` clobbers a manually-marked question** if both fire on the same chunk window. | Low | Medium | Both prepend onto `questions[0]`; newest-first ordering is preserved. The dedup window (T-2.4) prevents the auto path from re-asking text the user just manually marked. AC-5 test confirms structural independence. |
| **`store.markAuto` throw propagates out of the worker and crashes the drain loop.** | Low | High | Worker wraps `markAuto` in try/catch; failure is reported via `onItemError` but does NOT block dequeue progression. Test 21 covers this. |
| **Test environment lacks `crypto.randomUUID` / `performance.now` (Bun on CI vs. local).** | Low | Low | Worker accepts `now: () => number` and `generateId: () => string` injection (mirrors T-2.5 queue construction shape). All time-sensitive tests use fake clocks; identity-sensitive tests use a deterministic minter. |

## Hand-off to T-2.7 / T-2.8 / T-2.9

- **T-2.7 (cost guard)** reads each item's forwarded `usage` event from `onItemDone(result)` (`result.usage` + `result.costUsd`). Worker exposes the forwarded shape verbatim from `askClaude` so the cost guard adapter can sum across items without touching the worker internals.
- **T-2.8 (UX)** wraps the worker in a React hook (`useQueueWorker`) that mirrors `useAskClaude`'s `{ status, text, error, usage, costUsd, cacheReadRatio }` shape. The AnswerPanel re-uses verbatim. The `method: "auto"` badge ships in the header.
- **T-2.9 (settings)** drives `maxDepth` (queue construction) + `enableHaikuFilter` toggle (skips `ask` when heuristic confidence < threshold). Worker takes both as injected dependencies; no settings-store coupling at the worker layer.
