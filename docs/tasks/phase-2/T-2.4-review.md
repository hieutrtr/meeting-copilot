Sliding-window non-refresh invariant (anti-stutterer guarantee): a duplicate hit does **not** extend the entry's lifetime; expiry is anchored to the original admit time. Test `does NOT refresh the window on a duplicate hit` covers this — admit at t=0, dup at t=30k, dup at t=50k, fresh admit at t=60k+1.

### Per-call cost projection (for T-2.7 cost guard input)

Pure-JS function — **$0.000000 / call**. No LLM call, no network, no SDK overhead. The dedup layer is a cost *reducer* for downstream Sonnet (`askClaude()`) by suppressing duplicate-question answer fires; T-2.7 owns the meeting-wide Haiku cost guard, which the dedup window does not interact with directly.

### Latency

Pure synchronous JS (`normalize` → `fnv1a64` → `Map.get/set/walk`). Worst-case per-call work for the upper bound of "1000 distinct questions in 60 s" (16 q/s sustained, totally unrealistic) = O(1000) Map walk + O(len(text)) hash + O(len(text)) regex normalization. On a typical meeting (≤ 10 candidates / min) the map size stays ≤ 10 and per-call latency is sub-microsecond — well under the < 100 ms assembler-stage budget per ARCH §12.

## Hand-off to T-2.5

T-2.5 (bounded queue) consumes the dedup result after the Haiku threshold gate. Stable integration shape:

```ts
// In the queue worker (T-2.5):
const dedup = createDedupWindow({ windowMs: settings.dedupWindowMs });
// ... per utterance:
const dedupResult = dedup.admit(utt.text, utt.startTs);
if (!dedupResult.admitted) {
  log("dedup-rejected", {
    hash: dedupResult.hash,
    matchedAt: dedupResult.matchedAt,
  });
  return;
}
queue.push({ utterance: utt, verdict, dedupHash: dedupResult.hash });
```

T-2.5 owns the lifetime: instantiates one `DedupWindow` per meeting, calls `reset()` on meeting end / `meetingStore.startNew()`. T-2.9 settings will wire the `windowMs` slider value into the constructor at meeting start.
