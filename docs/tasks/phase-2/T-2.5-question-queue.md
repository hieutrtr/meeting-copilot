## Scope

A pure factory `createQuestionQueue(opts)` returning a single-flight bounded queue. No global mutable state (one `QuestionQueue` instance per meeting; lifetime ≅ `meetingStore.startNew()` to `meetingStore.end()`).

```ts
export interface QueuedItem {
  id: string;                 // stable UUID-ish (`q-…`); reused as `Question.id` downstream
  meetingId: string;          // meeting scope; persistence adapter uses this for namespacing
  utterance: Utterance;       // T-2.2 boundary
  verdict: HaikuVerdict;      // T-2.3 subset (isQuestion + confidence + reason)
  dedupHash: string;          // T-2.4 hash; carried for telemetry / future cross-meeting dedup
  enqueuedAt: number;         // ms since epoch (or injected clock)
}

export type DropReason = "backpressure";

export interface EnqueueResult {
  admitted: boolean;
  itemId: string;
  droppedItemIds?: string[];  // populated when admitted === true && backpressure dropped older items
  reason?: DropReason;        // populated when admitted === false (queue full of newer items, but spec says drop-OLDEST so this branch is unreachable v0.2 — kept for future)
}

export interface QueuePersistenceAdapter {
  load(): QueuedItem[];                  // sync read on construct (one disk hit per meeting)
  save(items: QueuedItem[]): void;       // sync write after every mutation; idempotent
  clear(): void;                         // hard wipe — called on `queue.clear()`
}

export interface CreateQueueOptions {
  maxDepth?: number;                     // default 5 (per ARCH §3 single-flight + plan)
  persistence?: QueuePersistenceAdapter; // default: noop in-memory (no checkpoint)
  now?: () => number;                    // injectable clock for tests
  generateId?: () => string;             // injectable ID generator for tests
}

export interface QuestionQueue {
  enqueue(input: EnqueueInput): EnqueueResult;
  dequeue(): QueuedItem | null;          // moves head → in-flight slot; null if busy or empty
  complete(itemId: string): boolean;     // true if itemId matched in-flight slot
  fail(itemId: string, reason?: string): boolean;
  pending(): QueuedItem[];               // shallow copy, safe for React state
  inFlight(): QueuedItem | null;         // current single-flight slot (null when idle)
  size(): number;                        // pending count (NOT including in-flight)
  isBusy(): boolean;                     // shorthand for inFlight() !== null
  clear(): void;                         // drop pending + in-flight; calls persistence.clear()
}

export interface EnqueueInput {
  meetingId: string;
  utterance: Utterance;
  verdict: HaikuVerdict;
  dedupHash: string;
  id?: string;                           // optional override (e.g. when caller already minted)
}

export const DEFAULT_MAX_DEPTH = 5 as const;

export function createQueuePersistenceAdapter(
  store: Map<string, QueuedItem[]>,
  meetingId: string,
): QueuePersistenceAdapter;                // canonical Map-backed adapter (used in tests + as ref impl)

export function createQuestionQueue(opts?: CreateQueueOptions): QuestionQueue;
```

### Drop-oldest semantics (v0.2)

Per plan AC: drop-oldest when depth > 5. Concretely, after a fresh admit:

1. If `pending.length + 1 ≤ maxDepth` → push to tail; admitted.
2. If `pending.length + 1 > maxDepth` → **shift the oldest** items off the head (one or more, until depth is `maxDepth - 1`), then push new item to tail. **The new item is always admitted.** Returned `EnqueueResult.droppedItemIds` lists the dropped ids in eviction order (oldest first). Dropped items are logged with `reason: "backpressure"` by the caller.

Rationale: the freshest question is the most likely to still be relevant — older items in a backpressured queue are likely already stale (the answer is no longer needed). This matches the ARCH §3 single-flight policy and the plan AC verbatim.

### Single-flight invariant

- At most one item is "in-flight" at any time. `dequeue()` is the only transition into in-flight; `complete()` / `fail()` are the only transitions out.
- `dequeue()` returns `null` when `inFlight() !== null` even if `pending` is non-empty. The caller (T-2.6) is expected to drive a worker loop:

```ts
function tick() {
  if (queue.isBusy()) return;
  const next = queue.dequeue();
  if (!next) return;
  askClaude(next.utterance.text)
    .then(() => queue.complete(next.id))
    .catch((err) => queue.fail(next.id, String(err)));
}
```

- The JS event loop guarantees the busy flag flip is atomic (no torn-state risk between `isBusy()` check and `dequeue()` set). No mutex needed.

### Persistence semantics

- The adapter is **optional**. When omitted, the queue is purely in-memory; `pending()` returns `[]` after process restart.
- When provided, every mutating operation (`enqueue` admit, `dequeue` move-to-flight, `complete`, `fail`, `clear`) ends with `persistence.save([...pending, ...inFlight])` so a crash mid-operation loses at most the *current* mutation. We persist the **union of pending + in-flight** so on cold-start `load()` the worker can restart any mid-flight item from scratch (idempotent retry — safe because Sonnet calls are pure-prompt-in / answer-out).
- The default ref implementation is `createQueuePersistenceAdapter(map, meetingId)` — a `Map<meetingId, QueuedItem[]>`-backed adapter. In tests we instantiate a shared `Map`, build queue A, mutate, drop the reference, build queue B with the same map, and assert queue B's `pending()` matches queue A's last-saved snapshot.
- Production wiring (Phase 2.x): a `localStorage` adapter using `meeting-copilot.queue.<meetingId>` as the key (cheap, JS-side, works in Tauri webview without IPC); a SQLite adapter via a future `helper_daemon::Repo::save_queue_checkpoint` Tauri command if measured failure rates demand stricter durability. Both are out of scope for T-2.5 — the interface is the deliverable here.

### Hand-off contract

T-2.6 imports `createQuestionQueue` and runs the worker loop. It also pushes onto the existing `useQuestionStore.questions` (T-1.9) so the AnswerPanel renders. T-2.7 reads `inFlight()` for cost telemetry. T-2.9 reads `maxDepth` from settings (slider exposes 1–10 range; default 5).

## Acceptance Criteria

Verbatim from plan (T-2.5):

> Bounded queue (max 1 concurrent answer generation, drop oldest if > 5). AC: stress test 20 q/min không crash.

Translated to numeric AC:

1. **AC GATE — stress test 20 q/min for 60 s.** Drive 20 enqueues evenly spaced over 60 s of fake-timer simulation. Queue never crashes; all enqueues either admit or are dropped via documented `backpressure`. Final `pending().length + dropped.length === 20 - completed.length` (conservation). With `maxDepth = 5` and a single in-flight slot processing each item in 1 s of fake time, the steady-state pending depth never exceeds 5; drop-oldest fires at least once when an admit pulse hits depth-6 boundary.
2. **Drop-oldest invariant.** With `maxDepth = 3`, enqueue 5 items in rapid succession (no dequeue between). After the 5th admit: `pending().length === 3`, the **last 3** ids are present, and `EnqueueResult.droppedItemIds` from the 4th and 5th admits each include exactly 1 id (the oldest at that moment).
3. **Single-flight invariant.** After `dequeue()` a 1st item, `dequeue()` returns `null` until `complete()` or `fail()` is called, regardless of `pending().length`. After `complete()`, the next `dequeue()` returns the new head.
4. **FIFO ordering** (head-to-tail enqueue / dequeue order). 5 items enqueued in order → dequeued in order. `pending()` array reflects head-to-tail.
5. **Persistence — across reconstruct.** Construct queue A with persistence adapter `P`. Enqueue 3 items. Drop reference to A. Construct queue B with same adapter `P`. `B.pending()` returns the same 3 items in the same order. Mutate B (dequeue + complete one). Construct queue C — `C.pending().length === 2` and `C.inFlight() === null`.
6. **Persistence — in-flight item recovered as pending.** Queue A enqueues 1 item, dequeues it (moves to in-flight). Persistence snapshot now includes it in `pending + inFlight`. Reconstruct as queue B → `B.pending()` contains it (head position), `B.inFlight() === null`. Caller (T-2.6) treats this as a clean retry — Sonnet is idempotent on prompt-in / answer-out.
7. **Conservation under stress.** Over 100 admits with random complete / fail / drop events, `enqueue.admittedCount === complete.count + fail.count + dropped.count + pending.length + inFlight ? 1 : 0`. (Bookkeeping invariant.)
8. **clear() is total.** After `clear()`, `pending().length === 0`, `inFlight() === null`, and persistence `load()` returns `[]`.
9. **Independent queues.** Two `createQuestionQueue()` instances (different meeting ids, different adapters) do not share state. Mutations on one do not affect the other.
10. **complete() / fail() with stale id.** Calling either with an id that does not match `inFlight()` returns `false` and is a no-op (no throw, no state mutation).
11. **Empty-queue dequeue.** `dequeue()` on an empty queue returns `null` and does not flip `isBusy()`.
12. **Persistence adapter can be omitted.** With no adapter, the queue functions identically except `pending()` is empty across reconstruct (no checkpoint).

Test cases (target ≥ 25):

1. **Construction**
   - default `maxDepth === 5`.
   - injected `now()` controls `enqueuedAt`.
   - injected `generateId()` mints predictable ids.
   - persistence adapter optional (no throw when omitted).
2. **Enqueue + ordering**
   - first admit: `admitted: true`, `itemId` matches mint.
   - 5 in order → `pending()` returns them head-to-tail in mint order.
   - 5 with explicit `id` field → uses provided ids verbatim.
3. **Drop-oldest (drop = depth > maxDepth)**
   - `maxDepth: 3`, 4 admits → 4th's `droppedItemIds = [item1]`, `pending().length === 3` with items 2, 3, 4.
   - 5 admits same config → 4th drops [1], 5th drops [2]; `pending()` = [3, 4, 5].
   - bulk: `maxDepth: 3`, 10 admits in a tight loop → `pending().length === 3` with last 3 ids; 7 dropped total.
4. **Dequeue + single-flight**
   - dequeue empty → `null`, `isBusy() === false`.
   - dequeue with 1 pending → returns head, `inFlight()` populated, `pending().length === 0`.
   - second dequeue while busy → `null` even with pending depth > 0.
   - complete then dequeue → returns next head.
5. **complete / fail**
   - complete in-flight id → `true`, clears in-flight slot.
   - complete stale id → `false`, in-flight unchanged.
   - fail in-flight id → `true`, clears slot (logs reason but no throw).
   - fail stale id → `false`.
6. **Persistence**
   - adapter `save()` called after enqueue admit.
   - adapter `save()` called after dequeue (snapshot includes in-flight).
   - adapter `save()` called after complete (snapshot now excludes the completed item).
   - adapter `save()` called after fail.
   - reconstruct from non-empty adapter → `pending()` matches saved snapshot.
   - in-flight item from prior session loads as pending head (retry semantics).
   - `clear()` calls adapter.clear() and persists empty.
   - omitting adapter → enqueue still admits, no save calls (smoke).
7. **Stress (AC GATE)**
   - 20 q/min over 60 s of fake-timer time, `maxDepth: 5`, single-flight worker simulated → 0 crash, conservation holds.
   - 100 random ops (enqueue/dequeue/complete/fail/clear) with seeded RNG → conservation holds at every step (no negative counts, no torn state).
8. **Edges**
   - `maxDepth: 1` — every admit drops the prior pending head if any.
   - independent queues with different adapter Maps — mutations isolated.
   - empty utterance text still admits (the queue is text-agnostic; T-2.4 dedup is the empty-string filter).
   - persistence adapter that throws on save → enqueue still returns admitted=true (we don't roll back on a save failure; the bug shows up on next reconstruct, telemetry-only). Test asserts the save error does NOT crash the queue.

## Risk + Mitigation

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| **Race between `dequeue` busy-check and a synchronous concurrent `enqueue`** | Low | Low | JS event-loop guarantees: enqueue and dequeue both run on the main thread; there is no preemption between `isBusy()` and the busy-flag flip inside `dequeue()`. Test asserts the invariant via tight-loop interleaving. |
| **Drop-oldest evicts in-flight item by mistake** | Low | Medium | In-flight slot is structurally separate from `pending` — the eviction loop only walks `pending`. Test enqueues to depth, dequeues 1 (moves to in-flight), enqueues to depth+maxDepth → asserts in-flight survives, only pending gets evicted. |
| **Persistence adapter latency stalls enqueue path** | Medium | Medium | `save()` is sync in the interface; in-memory and localStorage adapters are sub-millisecond. SQLite adapter (future) lands behind a debounce / batched-write wrapper if real measurements warrant. T-2.5 ships only the interface and the in-memory ref impl; perf risk does not materialize until T-2.6 + Phase 2.x SQLite wire. |
| **In-flight item lost on crash mid-stream** | Medium | Low (degraded UX, not data loss) | Persistence snapshot includes both pending and in-flight. On reconstruct, in-flight items are re-injected as pending head → worker retries. Sonnet calls are stateless prompt-in / answer-out so retry is safe. The Phase-2 user-visible behavior is "answer for the last detected question is delayed by ≤ 1 stream-restart cycle"; not a correctness issue. |
| **Backpressure spam: detector floods queue** | Medium | Medium | Drop-oldest caps the working set at `maxDepth` (default 5). T-2.7 cost guard fires the user-visible alert; T-2.9 settings exposes slider 1–10 so paranoid users can shrink the queue to 1. |
| **`maxDepth = 0` or negative** | Low | Low | Constructor clamps to `Math.max(1, opts?.maxDepth ?? DEFAULT_MAX_DEPTH)`. Test asserts `maxDepth: 0` behaves as 1. |
| **Persistence schema drift across versions** | Low | Medium (data-corruption flavor) | Persistence adapter stores `QueuedItem` JSON verbatim; the schema is the TS interface. Phase 2.x will add a `version: "1.0.0"` envelope when the first additive field lands; for v0.2 the in-memory adapter is the only ref impl, so the drift surface is zero. |

## Out of Scope (explicitly deferred)

- **SQLite-backed persistence adapter via `helper_daemon::Repo`** — requires a new Tauri command (`save_queue_checkpoint` / `load_queue_checkpoint`) + Rust handlers + an idempotent DDL migration adding a `pending_questions` table or a JSON-blob column on `meetings`. Per INDEX line 51 ("Optional SQLite checkpoint via `Repo`") this is *optional*; T-2.5 ships the interface seam so the wire-up is a drop-in v2.x. Failure mode that would force this in: T-2.10 metric report shows > 5% data loss on real-meeting crash recovery (currently unmeasured).
- **localStorage adapter** — even simpler to ship than SQLite (no Rust changes), but per loop step description T-2.5 focuses on interface + in-memory ref impl. T-2.9 settings task may add this if user-visible "auto-recovery" is exposed there.
- **Cross-meeting persistence** — `meetingId` namespacing is in the interface but no test covers two-meeting re-hydration in T-2.5; deferred to T-2.6 / E2E.
- **Priority queue / fairness** — flat FIFO. No "important question" jumping the line. Future Phase 3 may add a priority lane (manual-marked > auto-detected) but the spec is plain FIFO.
- **Persistence write batching / debounce** — sync on every mutation. Optimization deferred; in-memory ref impl makes this a non-issue.
- **Telemetry events** — drop / admit / complete logs are caller-side responsibility (T-2.6 wires these into the existing logger); the queue itself is silent.
- **Cancellation of in-flight item** — `useAskClaude` (T-1.11) owns request-id-gated cancellation; T-2.5 only owns admit / single-flight. Composing the two is T-2.6's job.

## Hand-off to T-2.6 / T-2.7 / T-2.9

- **T-2.6 auto-trigger** — imports `createQuestionQueue`, instantiates one per meeting, runs a worker loop driven by either a `setInterval(50ms)` poller or a `useEffect` that re-runs on `pending()` changes. Calls `askClaude(next.utterance.text)` (T-1.10) and on settle calls `complete()` / `fail()`. Emits the AnswerPanel update via `useQuestionStore` (T-1.9 surface, `markAuto` companion to `markFromChunks`).
- **T-2.7 cost guard** — observes `inFlight()` snapshots to attribute Sonnet usage to the right `QueuedItem.id`; uses Haiku usage from `HaikuClassification` upstream (already on the queued item via `verdict`). The queue itself is free.
- **T-2.9 settings** — exposes `maxDepth` slider (range 1–10, default 5) and a "Restore in-flight on restart" toggle (default ON, controlling whether the persistence adapter is wired). Slider value flows into `createQuestionQueue({ maxDepth })` at meeting start.

Integration sketch for T-2.6:

```ts
const queue = createQuestionQueue({
  maxDepth: settings.queueMaxDepth,
  persistence: createQueuePersistenceAdapter(localCheckpointStore, meetingId),
});

// In the detector pipeline (T-2.1 → T-2.2 → T-2.3 → T-2.4 → here):
const dedupResult = dedup.admit(utt.text, utt.startTs);
if (!dedupResult.admitted) return;
const { admitted, itemId, droppedItemIds } = queue.enqueue({
  meetingId,
  utterance: utt,
  verdict,
  dedupHash: dedupResult.hash,
});
if (droppedItemIds?.length) {
  log("queue-drop", { reason: "backpressure", droppedItemIds });
}

// Worker loop (single-flight):
useEffect(() => {
  if (queue.isBusy()) return;
  const next = queue.dequeue();
  if (!next) return;
  const ctrl = new AbortController();
  askClaude(next.utterance.text, { signal: ctrl.signal })
    .then(() => queue.complete(next.id))
    .catch((err) => queue.fail(next.id, String(err)));
  return () => ctrl.abort();
}, [queue.size(), queue.isBusy()]);
```
