## Findings (to feed the spike memo)

1. **Two AVAudioEngine instances coexist in one process — code path proven.** The dual-engine init (one default-mic, one BlackHole-redirected via `AudioUnitSetProperty(kAudioOutputUnitProperty_CurrentDevice)`) compiles, type-checks, and reaches the BlackHole-presence guard in `parallel` mode. This was the single largest structural risk for UNKNOWN #1 — appears to clear. Numeric drift / glitch evidence pending install.
2. **The redirect primitive is the same in both modes.** Whether the target is "BlackHole 2ch" or a user-built "MeetingCopilot Input" Aggregate Device, the engine-to-device wiring is one `AudioUnitSetProperty` call. Phase 1 audio backend (T-1.2) can support both modes with the same code path differing only in `target_device_id`. ScreenCaptureKit fallback (ARCH §2.2) is a *different* code path; the redirect primitive doesn't apply there.
3. **`mach_absolute_time()` is the only viable cross-engine time base.** `AVAudioTime.sampleTime` is per-engine, per-device — not comparable across the two engines in `parallel` mode. Sync-offset measurement uses `firstCallbackHostTime` (set inside the tap on the first buffer arrival). This convention is encoded in the spike and should be reused in the production daemon's diarization aligner.
4. **Pre-flight ordering matters.** The spike checks BlackHole / Aggregate presence *before* probing TCC, *before* installing taps, *before* starting engines. Each layer fails fast with its own exit code. Production health-check should follow the same ordering: enumerate → presence → permission → init → start. This means the onboarding wizard can render an actionable error at exactly the failing step, not generically "audio doesn't work".
5. **Drift evidence design: per-5s timeseries snapshot.** A JSONL append every 5s (~12 lines over 60s) is enough to plot drift trajectory and answer the question "does it grow linearly or saturate?" Cheaper than continuous logging; fine resolution for the diagnosis. The pattern is reusable in the daemon's drift-watchdog (re-anchor on next chunk boundary if drift > threshold).
6. **CPU sampling via `getrusage(RUSAGE_SELF)` is sufficient and cheap.** No need for `task_info` / `proc_pidtaskinfo`. Per-second snapshot of `(Δuser + Δsystem) / Δwallclock` gives percent of one core; we report avg + peak. Reusable in production daemon health endpoint.
7. **Parallel-mode is intentionally the *harder* test to run by default.** If parallel passes the drift bar, both modes are viable and we can ship the simpler (no-aggregate-required) UX. If parallel fails, aggregate is the explicit fallback. Defaulting to parallel pushes the spike to surface the worst case rather than mask it.

## Issues / pivot suggestions

The loop step explicitly asked the review to "nêu rõ pivot option (Electron + native helper) nếu fail". Pivot options are listed below in escalation order, with the trigger criterion for each:

1. **Pivot 1 (lightweight) — switch production default from `parallel` to `aggregate`.**
   - Trigger: post-install run shows `cross.drift_ms_over_60s > 100` in parallel mode AND `cross.drift_ms_over_60s ≈ 0` in aggregate mode.
   - Cost: onboarding wizard gains one extra step (Aggregate Device construction in AMS). Code change is one config flag.
   - Confidence: high — kernel drift correction on aggregate devices is documented Apple behaviour, used by every macOS DAW.

2. **Pivot 2 (medium) — escalate UNKNOWN #1 to a ScreenCaptureKit spike.**
   - Trigger: post-install run shows BOTH modes fail the drift / sync / CPU bars (e.g., aggregate device drift correction is broken on this macOS version, or BlackHole introduces glitches under load).
   - Cost: insert a new T-0.3.5 spike that uses ScreenCaptureKit (`SCStream` with audio output) instead of BlackHole; ScreenCaptureKit is macOS 13+ only (acceptable per ARCH §1) and gives system audio without HAL plug-in. Estimated 1 day spike. Defers T-0.4 / T-0.5.
   - Confidence: medium — first-party API, but newer (less battle-tested in production audio pipelines), and Phase 0 budget tightens.

3. **Pivot 3 (heavyweight) — switch desktop framework from Tauri to Electron + native Swift helper.**
   - Trigger: post-install runs show that ScreenCaptureKit *also* fails OR the audio code path requires deeper integration with a framework Tauri can't reach (e.g., audio session management beyond `AVAudioEngine`).
   - Cost: re-open ARCH §8.1 framework decision, throw away T-0.8 Tauri scaffold (not yet written at this point in the loop), add ~1 week to Phase 0 / Phase 1. Electron's audio plugin ecosystem is more mature; the Swift helper handles capture out-of-process and IPCs PCM frames to the Electron renderer.
   - Confidence: low confidence we'll need this — Pivot 1 / 2 should resolve any plausible failure on Apple Silicon hosts. Listed for completeness because the loop step asked.

**Recommendation (preliminary, pre-install)**: assume Pivot 1 / Pivot 2 are sufficient. Do NOT pre-emptively switch to Electron. Let the post-install drift number drive the decision; the spike memo (T-0.6) will record which pivot fired.
