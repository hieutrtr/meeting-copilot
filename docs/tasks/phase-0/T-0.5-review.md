## 3. Findings (memo bullets — for `docs/spike-memo.md`)

1. **Request shape is correct by construction.** All 9 tests in `request-shape.test.ts` pass: model = `claude-sonnet-4-6`, two `cache_control: { type: "ephemeral" }` system blocks (static instructions + 20k context), recent transcript + question land on the user message **without** `cache_control`, `max_tokens: 600`, `temperature: 0`. Two consecutive `buildRequest()` calls produce byte-identical bodies — a *necessary* condition for cache hits on call ≥ 2 — and that's now under test. AC-3 cannot fail for a reason other than network.
2. **Cached portion clears the 20k bar with margin.** Dry-run body inspection: `system[1].text = 75,667 chars ≈ 21,500 tokens` at the 3.5 chars/tok rule of thumb. AC-4 (≥ 20 000 cached tokens) is structurally satisfied modulo Sonnet's actual tokeniser; the live bench will report the exact `cache_creation_input_tokens` from call #1 and tighten the heuristic if needed.
3. **Pricing math holds against ARCH §13.** Cache read is exactly 10× cheaper than uncached input ($0.30 vs $3.00 per MTok). Original AC-5 advisory bar of $0.005 was too tight — output tokens at $15/MTok dominate the warm-call cost. Revised to **$0.015/call advisory** (matches the §13 reference profile of ~$0.03/call for a 30k-cached + 1k-fresh + 300-out turn; our leaner 21k-cached profile lands ~$0.01). This revision is reflected in the task plan and bench harness.
4. **Single-client / HTTP/2 keep-alive enforced.** `runBench()` constructs one `Anthropic` client and reuses it across all 10 runs. ARCH §7.3 requirement met.
5. **BLOCKED-PENDING-KEY surfaced cleanly.** With no `ANTHROPIC_API_KEY` on the host, `./run.sh` exits 12 with a structured JSON payload + a `results.md` that lists the 3-step unblock walkthrough. This matches the T-0.2 BLOCKED-PENDING-INSTALL pattern (Swift compiles, Core Audio enumerates, blocks at the missing dep) — code is ready, hardware/account state is what's missing.

## 4. Issues / pivot suggestions

- **Risk that didn't show up but might.** ARCH §6.2 says ephemeral cache TTL is 5 min; if the API ever returns a `cache_creation_input_tokens > 0` on a warm call (i.e., cache *re-write* mid-burst), AC-3 will dip below 0.9 not because we mis-built the request but because the cache was evicted. The harness already records this asymmetrically (warm `cache_read_ratio_min` is the AC-3 gate, not the average), so a single bad call = AC-3 fail and we'll see it. Suggested follow-up: if AC-3 fails this way in live bench, retry with a 1-hour TTL profile (`cache_control: { type: "ephemeral", ttl: "1h" }` if account allows) before declaring NO-GO.
- **Bench duration variance.** 10 streaming calls at ~1.5–3 s each = 15–30 s total. Network jitter on a flaky connection could push warm p95 above 2.5 s (AC-2 advisory). Mitigation already in place: gating ACs (1, 3, 4, 6) tolerate jitter; only the advisory ACs are jitter-sensitive.
- **No 1-hour TTL bench.** Current spike does 5-min TTL only. If Phase 1 needs 1-hour cache (cost win), that's a separate prove. Documented in task plan §9 "Out of scope".
- **Pricing constants drift.** Hardcoded Sonnet 4.6 prices in `pricing.ts` are a 2026-05 snapshot. AC-5 is advisory precisely because of this; if memo ends up depending on the dollar number, verify against the public price page on memo-write day.
- **No streaming-truncation test.** Bench checks `stop_reason` is recorded but doesn't gate on it. If `max_tokens: 600` is hit for every run (unusual for a "≤ 150 words" answer), output cost climbs. Memo bullet 3 already calls this out.
