## Findings (to feed the spike memo)

1. **TCC `authorizationStatus(for: .audio)` is a synchronous, side-effect-free probe.** Phase 1 onboarding wizard can use it to render the right state (granted / pending-prompt / hard-denied) without firing the modal prematurely. Recommend: status check on app start; only call `requestAccess` from a user-driven UI button. Logged in `mic_capture.swift:55–72`.
2. **`AVAudioEngine.inputNode` (or `outputFormat(forBus:)`) blocks indefinitely on `.notDetermined` in headless contexts.** Observed: hung past 90 s with no progress, no error, no log. This is a sharp foot-gun for any future Rust `cpal`/`coreaudio-rs` daemon (T-1.2) — without an explicit auth probe + non-blocking init, the daemon will appear to deadlock to users on first run. Action item for T-1.2 design: add identical pre-flight in Rust (`AVCaptureDevice` via objc2/`coreaudio-rs` FFI) **before** opening the input device.
3. **`swiftc -O` against macOS 26.2 SDK compiles a 380-line AVAudioEngine CLI in ~1.5 s with zero warnings.** Single-file Swift is a viable spike harness for any further audio-side experiments in Phase 0 (T-0.2 ScreenCaptureKit, T-0.3 BlackHole route). No need to fight Xcode for the spikes.
4. **Architecture §2's stated approach (AVAudioEngine tap → 16 kHz mono PCM) maps cleanly onto a 50-line script** — most of the file is metrics/instrumentation, not API plumbing. That suggests T-1.2 (the real daemon) is mostly streaming-IPC + permission-UX work, not novel audio code. Effort estimate in the implementation plan (`L = 1.5 days` for T-1.2) feels right.
5. **The host this iteration runs on is M1 Max / 64 GB, not the M1 Pro / 16 GB target.** This is irrelevant for T-0.1 (capture works the same), but flag for T-0.3 / T-0.4 RTF benchmarks where the upgrade gives optimistic numbers — the spike memo must call this out so we don't over-promise.

## Issues / pivot suggestions

- **No pivot needed.** Mic side of unknown #1 is "expected to work, blocked only on user permission." The architecture's stated approach (AVAudioEngine + 16 kHz mono) is a one-line change away from working — instead of writing at native rate, install an `AVAudioMixerNode` between input and the tap with output format `AVAudioFormat(standardFormatWithSampleRate: 16000, channels: 1)`. Deferred to T-1.2 because the spike's job was prove-out, not perfect-fidelity.
- **Action for the loop driver / user**: before T-0.2 (system audio via BlackHole) is meaningful, the user needs to (a) grant Microphone permission to the parent terminal once, (b) install BlackHole-2ch + create the Aggregate Device. Both already documented in `INDEX.md` "Known Gaps". Surfacing again in the spike memo so it's not buried.
- **Tiny lint**: the task spec asked for "1 WAV file" in this slice — once permission lands, a future mic+system run will produce 2 WAV (T-0.3). The current script's CLI takes one WAV path and one metrics path; T-0.3 will fork into a dual-tap variant rather than re-use this script verbatim. That's the right shape (each task = one focused script).
