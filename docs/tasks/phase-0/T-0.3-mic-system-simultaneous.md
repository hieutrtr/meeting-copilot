## Acceptance criteria

Adapted from the loop step description ("60s test → results với numbers thật (ms drift, % CPU, glitch count). Output phải có verdict GO/NO-GO/CAVEAT preliminary"):

| AC | Target | Measured field |
|---|---|---|
| 60-second simultaneous recording produces 2 valid WAVs | both `mic.wav` + `system.wav` open in `afinfo`, durations within 1% of 60s | `mic.audio_seconds_recorded`, `sys.audio_seconds_recorded` |
| Per-stream glitch count is zero | `mic.glitch_count == 0` and `sys.glitch_count == 0` over 60s | per-stream metrics |
| Per-stream first-callback latency is bounded | both `< 500 ms` | `*.first_callback_latency_ms` |
| Cross-stream sync offset at start is bounded | `sync_offset_ms <= 50` (mic vs sys first-callback wallclock difference) | `cross.sync_offset_ms` |
| Cross-stream clock drift over 60s is bounded | `drift_ms <= 100` (audio_seconds_recorded difference between streams scaled to 60s) | `cross.drift_ms_over_60s` |
| Combined process CPU is bounded | average `<= 10%` of one core, peak `<= 25%` of one core | `cross.cpu_avg_pct`, `cross.cpu_peak_pct` |
| Reproducible | one command `./run.sh [duration]` rebuilds + reruns from scratch | n/a |
| Failure mode | distinct structured exit code + JSON `error` + `hint` for each blocked path | exit codes 5–11 |

**Pass-bar / verdict line in `results.md`**:
- 🟢 **GO** if all numeric ACs above pass.
- 🟡 **CAVEAT-GO** if hardware blocks the run but structural path (device enumeration + dual-engine init + tap install) succeeds (preliminary verdict; flips to GO once BlackHole installed + mic granted, expected zero code change).
- 🔴 **NO-GO** if dual AVAudioEngine instances cannot coexist OR drift > 100ms over 60s OR combined CPU > 25% (forces pivot — see review).

## Approach: spike with 2 modes

Two strategies for "mic + system audio simultaneously" are both viable per ARCH §2.1; the spike supports and times both so we can pick the production default:

### Mode A — `parallel` (default in spike)
Two independent `AVAudioEngine` instances in the same process:
- engine 1: default mic (no device redirect), single channel @ native rate.
- engine 2: redirected to BlackHole-2ch via `AudioUnitSetProperty(kAudioOutputUnitProperty_CurrentDevice)` (same redirect pattern as T-0.2).
- each engine has its own tap callback, its own WAV file, its own metrics.
- cross-stream sync offset = `firstCallbackHostTime[sys] − firstCallbackHostTime[mic]` (signed, ms).
- clock drift over duration = `(mic.audio_seconds_recorded − sys.audio_seconds_recorded)` scaled to 60s window.

**Pros**: zero AMS user-side configuration beyond the BlackHole install (already required by T-0.2). Two labeled streams from the start (we know which speaker is "me" vs "them").
**Cons**: separate sample clocks → measurable drift over time. We need to *measure* how bad to know if Mode A is shippable.

### Mode B — `aggregate <device-name>`
Single `AVAudioEngine` tapping a user-pre-built Aggregate Input Device (named `MeetingCopilot Input` per T-0.2 unblock spec). The kernel runs Drift Correction across the aggregate's sub-devices; mic + BlackHole arrive in one stream interleaved.
- one tap callback, two channels split into mic.wav + system.wav post-hoc.
- drift is corrected by the kernel — measurable as zero by definition; only sync offset is meaningful (and is zero by construction).
- this matches ARCH §2.1 production canon.

**Pros**: kernel-level drift correction, single audio path, lower CPU.
**Cons**: requires the user to pre-create the Aggregate Device in Audio MIDI Setup before running the spike.

The spike defaults to Mode A (`parallel`) because it's the harder of the two — if it passes, both modes are viable; if it fails (drift > 100ms / 60s), Mode B is the production fallback.

### Common code path (both modes)

- TCC pre-flight: `AVCaptureDevice.authorizationStatus(for: .audio)` — fails fast with structured `tcc_not_authorized` if not granted.
- BlackHole presence check: `kAudioHardwarePropertyDevices` enumeration + name-or-UID match (reused from T-0.2).
- watchdog: `duration + 12s` global timer; emits structured `watchdog_timeout` and `_exit(5)` if either engine wedges.
- CPU sampling: `getrusage(RUSAGE_SELF)` snapshots every 1s; `(Δuser + Δsys) / wallclock` = % of one core; record peak + average.
- per-stream metrics (mirrored from T-0.1 / T-0.2): callback count, sample count, first-callback latency, glitch count via `time.sampleTime` continuity, peak amplitude, dropout count via 50ms silence window.
- timeseries log: append a line every 5s to `out/timeseries.jsonl` with `{t_s, mic_audio_s, sys_audio_s, drift_ms, cpu_pct}` so growth-over-time is observable post-run.

### Structured exit codes

Mirroring T-0.2's six-code pattern, extending to the dual-stream context:

| Exit | Meaning | Hint |
|---|---|---|
| 0 | ok — all ACs pass | — |
| 5 | watchdog timeout | one engine wedged; check BlackHole permissions |
| 6 | tcc_not_authorized | grant Microphone access in System Settings |
| 7 | blackhole_not_installed | `brew install blackhole-2ch`; full AMS walkthrough in unblock steps |
| 8 | recorded but silent on system stream | system output not routed through Multi-Output Device |
| 9 | current_device_set_failed | redirect `AudioUnitSetProperty` failed — check HAL plugin |
| 10 | quality bar failed | recording succeeded but glitch / drift / CPU bar not met → NO-GO or CAVEAT |
| 11 | aggregate_device_not_found | mode B asked for an Aggregate Device that wasn't enumerated |

Verdict logic in `simul_capture.swift`: `exit 0` ⇒ 🟢 GO. `exit 7/6/9/11` ⇒ 🟡 BLOCKED-PENDING-(install/grant/setup) → preliminary CAVEAT-GO if structural-path checks reachable; report numbers we *did* get. `exit 10` ⇒ ambiguous (CAVEAT-GO with caveats listed, or NO-GO if the failed bar is drift). `exit 8` ⇒ CAVEAT-GO (system half silent — user-side AMS misconfig, not a code path bug).

## Reproduction

```sh
cd experiments/T-0.3
./run.sh                 # default: 60s, parallel mode
./run.sh 30              # short run, parallel mode
./run.sh 60 aggregate "MeetingCopilot Input"   # Mode B
```

Outputs:
- `out/run.log` — full stdout/stderr (compile + execute)
- `out/metrics.json` — structured cross-stream metrics (canonical)
- `out/mic.wav` — mic stream (post-success)
- `out/system.wav` — system stream (post-success)
- `out/timeseries.jsonl` — per-5s drift / CPU growth log
- `results.json` — auto-mirrored copy of `out/metrics.json`
- `results.md` — human summary + verdict line

## User unblock steps (manual, one-time; identical to T-0.1 + T-0.2 union)

1. **Grant Microphone permission** (T-0.1 prerequisite). System Settings → Privacy & Security → Microphone → enable for your terminal app. First run from interactive shell will surface the prompt.
2. **Install BlackHole-2ch** (T-0.2 prerequisite). `brew install blackhole-2ch`, approve system extension in Privacy & Security, reboot if prompted.
3. **(Mode A only) Audio MIDI Setup → Multi-Output Device** named `MeetingCopilot Output` (built-in speakers + BlackHole; drift correction ON for BlackHole) — set as system output during the run, play audio.
4. **(Mode B only, optional) Audio MIDI Setup → Aggregate Input Device** named `MeetingCopilot Input` (built-in mic + BlackHole; drift correction ON for BlackHole). Set as nothing — script targets it by name.

Verify with:
```sh
ls /Library/Audio/Plug-Ins/HAL/ | grep -i blackhole          # BlackHole2ch.driver
system_profiler SPAudioDataType | grep -E "BlackHole|MeetingCopilot"   # 2 lines if Mode A+B
```

## Open questions / notes

1. **Sample-clock domains in Mode A**: AVAudioEngine.inputNode's `AVAudioTime.sampleTime` is per-engine, so glitch detection per-stream is independent. Cross-stream timing must use `time.hostTime` (mach absolute time) — same wall-clock for both engines. The spike uses `mach_absolute_time()` → ns conversion via `mach_timebase_info` (already implemented in T-0.1 / T-0.2 as `nsBetween`).
2. **Drift sign convention**: positive `drift_ms` means mic is ahead of system audio (mic produced more wallclock-equivalent samples in the same elapsed time). Negative means BlackHole is ahead. Both directions matter for diarization.
3. **CPU baseline**: Apple Silicon M1 Max has 10 performance cores + 4 efficiency cores. We report % of *one* core (so 100% = saturating one core). The 10% / 25% bars are per-core not per-system, intentionally tight because the production daemon has many other consumers (whisper, Claude, MCP, UI).
4. **Pivot path if NO-GO**: per ARCH §2.2, the explicit fallback is **ScreenCaptureKit** (macOS 13+, native system audio API, deferred to v2). If Mode A fails the drift bar AND Mode B fails the AMS-setup UX bar, the loop driver should consider an early ScreenCaptureKit spike instead of postponing to v2. The review file will name this option explicitly.
5. **Why not a single `AVAudioEngine` with two tapped input nodes?** AVAudioEngine has exactly one inputNode per engine (singleton). The official multi-input pattern *is* the Aggregate Device (Mode B) or two engines (Mode A). No third option short of dropping AVAudioEngine for raw `AudioUnit`s.
6. **Why 50ms sync-offset bar?** Whisper's chunk granularity is ~250ms; question detection latency budget is ~500ms (PRD §1.2). 50ms keeps cross-stream alignment well under both. Tighter than the production daemon will need, intentionally — gives us headroom.
7. **Why 100ms drift over 60s?** A typical meeting is ~30-min. 100ms / 60s ≈ 1ms/sec ≈ 1.8s drift over 30 min — recoverable by periodic re-anchor on the next aggregate-device-friendly chunk boundary. Beyond that, diarization breaks.
