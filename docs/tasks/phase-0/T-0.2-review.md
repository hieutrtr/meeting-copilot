## Findings (to feed the spike memo)

1. **Core Audio device enumeration via `kAudioHardwarePropertyDevices` is permission-free.** Listing devices does not trigger the Microphone TCC prompt — only opening a device does. This is exactly the property the Phase 1 onboarding wizard needs: render "BlackHole detected? yes/no" *before* asking the user to grant permissions. Logged in `blackhole_capture.swift:enumerateDevices()` (~40 lines including channel count + nominal sample rate).
2. **`AudioUnitSetProperty(kAudioOutputUnitProperty_CurrentDevice)` cleanly redirects `AVAudioEngine.inputNode` to a non-default device.** Means a single-source spike does NOT need the user to first construct an Aggregate Device — that complexity belongs to T-0.3 (mic + system simultaneously). For the spike code path this is one Swift call; for the Rust daemon (T-1.2) the equivalent is `coreaudio-rs::AudioUnit::set_property(kAudioOutputUnitProperty_CurrentDevice, ...)`. Reusable pattern.
3. **The host has 2 unrelated virtual audio drivers already (Shure MOTIV Mix Virtual + ParrotAudioPlugin)** — neither is BlackHole. The script's name-match regex correctly excludes them. Worth noting for the wizard: a "looks like a virtual audio device" heuristic is wrong; need exact-name match against `BlackHole 2ch` / UID prefix `BlackHole2ch_UID`.
4. **BlackHole install is a single user-side blocker for *both* T-0.2 and T-0.3.** Once the user runs `brew install blackhole-2ch` + Audio MIDI Setup walkthrough, the entire system-audio leg of unknown #1 unlocks. Phase 1 onboarding wizard should bundle these steps; risk is the system-extension approval + reboot UX, not the technical capture path.
5. **Six exit codes is the right granularity for spike-stage diagnostics.** T-0.1 used 4 (`0`/`2`/`3`/`4`/`5`/`6`); T-0.2 needed `7` (BlackHole missing) and `8` (BlackHole present but recorded silence) on top. The "recorded silence" case is the *most likely* near-success failure — user installs BlackHole but forgets the Multi-Output Device step — so it deserves its own exit code rather than collapsing to "ok with peak=0".

## Issues / pivot suggestions

- **No pivot needed.** The spike's design is sound; the only "blocker" is a user install that the Phase 1 onboarding wizard already plans to walk through. Architecture §2.1's BlackHole-as-default decision is reinforced — alternatives (Loopback paid, ScreenCaptureKit) remain ARCH §2.2 fallbacks and are NOT in T-0.2 scope per the loop-driver rescope.
- **Action for the loop driver / user**: Before T-0.3 (mic + system simultaneously) is meaningful, the user needs to (a) `brew install blackhole-2ch`, (b) approve the system extension + reboot if prompted, (c) create both a Multi-Output Device AND an Aggregate Device in Audio MIDI Setup (the spec already lists step (c) under T-0.2 as "for T-0.3, not this task"), (d) play audio routed through Multi-Output. All four already documented in `INDEX.md` "Known Gaps" + this task's results.md.
- **Optional refinement (deferred to T-1.2)**: For production, the daemon should also `AudioObjectAddPropertyListener` on `kAudioHardwarePropertyDevices` so it reacts when the user plugs in BlackHole *while the app is running*. The spike doesn't need this; just noting for the daemon design.
- **Tiny note**: The 1-second warm-up window for dropout detection is a cheap heuristic that prevents false dropout flags from engine spin-up. Phase 1 may want a more principled "first audible buffer" anchor instead. Acceptable for spike.
