## Findings (to feed the spike memo T-0.6)

1. **UNKNOWN #2 prove: GO with massive margin.** Worst observed RTF on M1 Max is 0.256 (`large-v3-turbo` with hallucination loop on padded silence); best is 0.014 (`tiny`). Scaled to M1 Pro 16 GB target with a conservative 1.7× factor, worst-case RTF is ~0.435 — still 2.3× under the 1.0 bar. **Real-time STT on Apple Silicon is structurally feasible.** Phase 1 can default to local MLX without cloud dependency.

2. **`medium` is the sweet spot for Phase 1; `large-v3-turbo` is the eventual-Phase-2 upgrade.** `medium` gave 0.052–0.061 RTF (~16× headroom), 3.4 GB peak RAM, no hallucination, ~1.5s warm-load — production-ready out of the box. `large-v3-turbo` is faster on clean audio (0.041 on sample 1) but unstable on silence (0.221–0.256 on samples 2–5 due to the runaway-decode failure mode). Production `large-v3-turbo` requires VAD silence-trimming (per ARCH §2.4 spec — Silero VAD + 30s sliding window). Memo recommendation: **default Phase 1 to `medium`; flip to `large-v3-turbo` when T-1.5 wires VAD.**

3. **HF download is the user-perceived "first run" cost, not model load.** Cold load from disk is ~1.2–1.5s for all four models — fast enough for app startup. But sample 1 of `small`/`medium` showed 47s/138s "load" because the download is amortized into the first invocation. Phase 1 onboarding wizard MUST pre-download the chosen model during install or the first-meeting UX will be a 1–2 minute spinner. Add to T-1.11 settings panel scope or T-1.13 install-time scope.

4. **Memory profile fits 16 GB target with room for the rest of the stack.** Worst peak RSS is ~4.4 GB (medium first-sample transient); steady-state is ~3.4 GB. With Tauri (~150 MB), Claude streaming buffer (~50 MB), audio capture daemon (~50 MB), and OS overhead, total app footprint will be ~4 GB — comfortable on a 16 GB Mac with a Zoom call running in parallel.

5. **The runaway-decode failure mode is a real production risk, not just a benchmark artifact.** When `large-v3-turbo` hits silence with no EOS prediction, it generates ~10× more tokens than legitimate transcription, inflating compute cost. Real meetings have long silences (think-time, pauses between speakers). Without VAD, `large-v3-turbo` cost will be unpredictable and could drift from "0.04 RTF" to "0.25+ RTF" on any meeting with silence. This finding tightens ARCH §2.4 from "VAD is nice to have" to "VAD is required for the recommended production model."

## Issues / pivot suggestions

The verdict is GO so no pivot is required. Listed for completeness in case post-spike re-measurement on the M1 Pro target reveals issues:

1. **If M1 Pro 16 GB measurement comes back > 0.7 RTF for the chosen model:** drop one model tier. Order: `large-v3-turbo` → `medium` → `small`. `tiny` is too low-quality for production per public WER (medium ≈ 9% vs tiny ≈ 17%) and is reserved for fallback / underpowered devices.

2. **If MLX cold-start becomes a UX blocker in Phase 1:** ship a "warm pool" — a daemon that keeps the chosen model loaded across meetings. ARCH §2.5 already has the helper-daemon pattern; pre-warming the STT engine inside it is one config flag.

3. **If users on Intel Macs / non-Apple-Silicon report wanting the app:** Deepgram Nova-2 (already named as the official fallback in `IMPLEMENTATION-PLAN.md` line 38) is GO ready — quote ~$0.26/hour, hosted, no client compute. Phase 3 task or settings toggle.

4. **Streaming RTF (T-1.5) re-measurement is the next gate, not a pivot.** Batch RTF here (this task) is necessary-not-sufficient. T-1.5 will spawn a streaming wrapper that adds chunk overhead; expect 1.2–1.5× slower vs batch. Even at 1.5× from the worst observed `medium` (0.061 → 0.092), we're still 11× under the bar — but the *measurement* is required before Phase 1 ships.
