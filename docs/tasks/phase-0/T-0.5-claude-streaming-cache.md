```
  results.json
  README.md
```

**Layered TDD cycle:**

1. **Red** — write `request-shape.test.ts` asserting the shape from ARCH §7.2 (two cache breakpoints, recentTranscript NOT cached, model = `claude-sonnet-4-6`, max_tokens = 600). No SDK calls — just inspect the body that `buildPrompt.ts` produces.
2. **Green** — implement `buildPrompt.ts` to satisfy that test.
3. **Red** — write `pricing.test.ts` asserting cache-hit cost is ~10× cheaper than uncached for the same usage row.
4. **Green** — implement `pricing.ts`.
5. **Red** — write `live-bench.test.ts` asserting AC-1/3/4/6 over 10 runs.
6. **Green** — implement `streamBench.ts` + `run-bench.ts`. Live test is the long-running one; the runner script is a thin wrapper that reuses the same harness so test = production parity.

Tests 1+2 run with **zero key**, prove the structural correctness of the request, and gate before any spend. Test 3 is the actual spike measurement.

## 5. Hardware / env constraints

- **Apple Silicon**: irrelevant (pure network).
- **Network**: stable broadband (>50 Mbps suggested) — first-token latency includes round-trip + initial TLS handshake. Single keep-alive client across 10 runs to amortise.
- **API key**: `ANTHROPIC_API_KEY` env var. Per INDEX §"Toolchain Prerequisites": **STOP T-0.5 if missing.** Bench should exit with structured `exit 12 / api_key_missing` and an actionable message — never silently skip.
- **Rate limits**: 10 calls × ~30k tokens-counted-once-against-RPM ≈ trivial; default Sonnet RPM cap (4000/min) is not in play.
- **TTL behaviour (the named risk)**: ephemeral cache TTL = 5 min default per ARCH §6.2. The 10 calls run back-to-back inside ~1 min, so all calls ≥ 2 should hit warm cache. Bench records timestamp deltas and surfaces a warning if any inter-call gap > 4 min (would invalidate the AC-3 measurement).

## 7. Failure modes (documented up-front so review can check)

| Mode | Detection | Action |
|---|---|---|
| `ANTHROPIC_API_KEY` missing | env check at start | exit 12, write `results.md` BLOCKED-PENDING-KEY, STOP per loop rule |
| First-token avg ≥ 2000 ms | AC-1 fail in `live-bench.test.ts` | NO-GO for UNKNOWN #3 → memo recommends warmup ping or different model |
| Cache hit < 90% on call 2 | AC-3 fail | investigate: TTL miss? prompt order changed? same request body byte-for-byte? |
| Context < 20k cached tokens | AC-4 fail | `buildPrompt.ts` bug — pad more or document why |
| Network error mid-stream | exception in `streamBench.ts` | retry once with `min(2^k, 8)s` backoff; if 3 retries fail → AC-6 fail |
| Cache invalidation between runs | warning when `cache_creation_input_tokens > 0` on calls ≥ 2 | record in results, surface in review (does not gate AC unless it pushes ratio < 90%) |
| `bun` not in path | `which bun` at top of run.sh | exit with install hint |

## 8. Open questions / notes

1. **Streaming SDK shape.** Use `client.messages.stream()` (high-level helper) — emits `text` events; first-token = first non-empty `text` event. Alternative is `messages.create({ stream: true })` raw SSE; harder to time but more transparent. Picking `.stream()` for T-0.5; if it hides the `message_start` usage we'll downshift to raw SSE.
2. **Token-count for "20k context".** Spec says 20 000 tokens. Sonnet tokeniser is approximately ~3.5 chars/token for English prose; aim for ~70 000 chars to be safe. We'll over-pad to 75 000 chars and truncate after a `cache_creation_input_tokens` measurement on dry-run-1.
3. **Single client vs new client per call.** ARCH §7.3 mandates single client (HTTP/2 keep-alive). Bench respects that.
4. **Pricing constants.** Hardcode Sonnet 4.6 prices from public price page as of 2026-05: `$3/MTok input`, `$3.75/MTok cache write`, `$0.30/MTok cache read`, `$15/MTok output`. If prices have shifted, AC-5 advisory only — not a gate.
5. **Determinism.** `temperature: 0` on every call. Output token count varies a bit, but cost calc tolerates that (we measure actual `usage.output_tokens`).
6. **What goes in `recentTranscript`.** Use a fixed 90-second mock transcript (~150 words) — same string every run so it doesn't influence first-token-latency variance.
7. **Should the bench measure cold-start (no cache) baseline?** Yes — call 1 is cold; calls 2–10 are warm. We report both bands separately so the memo can say *cold ~2.4s, warm ~1.3s* (pretend numbers; real ones go in `results.md`).
8. **`stop_reason` sanity.** All runs should end `end_turn` or `max_tokens`. Anything else → log + AC-6 fail.
